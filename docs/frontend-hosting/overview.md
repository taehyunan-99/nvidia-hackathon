# 프런트엔드·호스팅을 위한 에이전트 조사

조사일: 2026-09-25. 기준 커밋: `c6945e61c58ff20a79814d64538889d599d6976b`. 작업 브랜치: `docs/frontend-hosting-plan`.

## 목적과 읽는 순서

분석 로직이 완성되기 전에 서비스 담당자가 **무엇을 입력받고, 어떤 상태를 보여주며, 어떤 결과·파일을 저장하고 연결해야 하는지** 확인한다. 실제 로직의 형식·분석 수치·호스팅 요구량을 추측한 사실로 기록하지 않는다. 후속 사용자 요청에 따라 [임시 서비스 규격 v0.1.0](temporary-contract.md)을 먼저 정했으며 실제 로직과 adapter로 연결한다.

| 문서 | 답하는 질문 |
|---|---|
| [에이전트 로직](agent-logic.md) | 어떤 자료 상태에서 실행·생략·보류가 갈리며 무엇이 남는가? |
| [프런트 연동 요구](frontend-contract.md) | 화면별로 어떤 데이터가 필요하고 3D·표·진행 상태를 어떻게 연결하는가? |
| [호스팅 요구](hosting-requirements.md) | 서버에서 무엇을 실행·저장하며 배포 전에 무엇을 실측해야 하는가? |
| [임시 입출력 규격](temporary-contract.md) | 로직 완성 전에 어떤 필드·응답·예시로 서비스 작업을 시작하는가? |

프로젝트 목적은 [HER2 개요](../topics/her2/overview.md), 기능 완료 기준은 [PRD](../PRD.md), 기술 선택은 [ARCHITECTURE](../ARCHITECTURE.md)·[ADR](../ADR.md)이 원본이다. 이 조사는 [실행 계획 S-01·G1](../plan.md)의 서비스 소비 요구를 구체화한다. S-01의 실제 Mol*·Docker 실험까지 완료한 기록은 아니다.

## 확인 수준

| 구분 | 이번에 확인한 범위 |
|---|---|
| 저장소 확인 | 서비스 소스·API 구현·Docker 배포 설정·분석 결과 파일은 없다. 공통 에이전트 도구의 코드는 서비스 구현과 구분했다. |
| 기존 설계 | 후보 2–3개, 입력부터 결과 보고까지의 범위, React·Mol*·FastAPI·worker·PostgreSQL 구성과 상태·연동 초안 |
| 임시 규격 작성 | v0.1.0 JSON Schema·9개 합성 시나리오와 ID·상태 검증. 실제 서비스·로직 계약 확정과 구분 |
| 외부 자료 확인 | 공식 Mol*·NVIDIA·FastAPI·Docker·AWS 문서, RCSB의 1N8Z·1S78 메타데이터와 원본 mmCIF 파일 |
| 실행하지 않은 검증 | 접촉·충돌 계산, 과학적 판정, NVIDIA 모델 호출, 패키지 설치·호환성 검사, 브라우저 3D 렌더링, Docker·AWS 배포·부하 측정 |

외부 문서의 지원 기능은 우리 계정·입력에서의 성공을 뜻하지 않는다. 본문에서 **기존 설계 / 이번에 관찰한 사실 / 임시 서비스 계약 / 실제 로직과 검토할 항목**을 구분한다. 후속 임시 규격의 키·타입·enum은 개발 기준으로 사용할 수 있으며 최종 로직 규격을 의미하지 않는다.

## 이번 사용자 인터뷰

| 항목 | 2026-09-25 답변과 반영 | 남은 경계 |
|---|---|---|
| 서비스 접근 | “누구나 실행·열람” | 로그인 여부·실행량 제한·타인의 개별 자료 열람 정책까지 정한 것은 아님 |
| 입력 진입 | “준비된 예제 선택 + 직접 입력·업로드” | 실제 예제 후보·서열·분석 구간·허용 파일 크기는 로직 담당과 검토 |
| 대상 기기 | “PC중심” | 모바일 동등 3D 성능을 추가 요구로 두지 않음 |
| 로직 연동 현황 | “로직에 대한 예시나 방식 등 정해진건 전혀 없어. 우리가 첫 작업” | 기존 ARCHITECTURE의 API·상태·스키마 설명은 구현 계약이 아닌 초안 |
| 임시 계약 진행 | 먼저 입출력 규격을 정하고 프런트·호스팅 작업을 진행한 뒤 로직에 맞춰 수정하는 방식 요청 | v0.1.0은 서비스 개발 기준으로 사용, 실제 로직은 adapter에서 대응 |
| 자료 공개·보관 | 공개 목록 없이 본인만 임시 조회·다운로드하는 방식 선택. 사이트 이탈 시 삭제 희망 | 사용자에게 방식 추천을 요청받아 마지막 세션 연결 후 30분 유예·만료 삭제를 초기 설계안으로 제시. 실측·구현 검증 전이며 즉시 삭제 보장이 아님 |
| 허용 데이터 | “공개 자료만 허용” 확정. 직접 입력·업로드도 동일한 범위 | 비공개 자료 지원은 이번 데모에서 제외하고 이후 별도 검토 |
| 호스팅 예산·일정·계정·도메인 | 결과 발표까지 가동, 탈락 시 종료, 좋은 성과면 유지 검토. 계정·도메인은 미정 | 정확한 날짜·예산 상한·유지 조건은 미확정 |

공개 입력·임시 결과 방식은 사용자 결정이고, 30분 유예는 추천을 요청받아 제시한 설계안이다. 남은 질문은 예산 상한, 정확한 가동 날짜, 실제 후보·구간·판정 기준, 모델 제공 경로·공개 실행 이용 조건, 세션 접근 방식과 실행 중 정리 동작이다. 조사·측정으로 확인할 사실을 사용자에게 추측해 답하도록 요구하지 않는다.

## 다음 공동 검토와 시작 가능한 작업

| 순서 | 준비·검토할 것 | 완료 증거 |
|---|---|---|
| 1. 입력과 구조 | 로직 담당이 실제 후보·분석 구간·assembly·사슬·잔기 대응을 검토. 서비스는 예제 선택과 직접 입력의 동일한 접수 요건 제시 | [D1·D2](../plan.md)의 출처 있는 입력 묶음과 대응표 |
| 2. 최소 연동 계약 | 정상·판단 보류·실행 실패의 필수 정보, ID 관계, 파일·진행 전달 방식 공동 검토 | [프런트 소비 요구](frontend-contract.md)를 생산자·소비자가 대조하고 필드·타입·필수성 확정 |
| 3. 독립 서비스 준비 | 화면 흐름·빈 상태·오류 표시 설계, 공개 구조 viewer 실험, Docker 의존성 조사 | 모의 표시임을 구분한 화면, 실제 구조 선택 검사, 실행 환경 확인 기록 |
| 4. 실제 연결·배포 | 실제 결과로 모의 응답 교체, 자원 실측, 공개 실행의 한도·자료 정책 확정 | 같은 실행의 화면·JSON·CSV·구조 일치, 재접속·중단·복구 검증 |

위 공동 검토가 끝나기 전에도 v0.1.0으로 화면·mock API·worker 운영·Docker 작업을 시작한다. 실제 데이터·모델 경로의 확인은 실제 연결·배포 검증 때 수행한다. 호스팅 가격 비교나 프런트 디자인 확정을 이번 로직 조사의 결론으로 대신하지 않는다.
