# 프런트엔드가 소비할 데이터와 상태

조사일: 2026-09-25. **연동 계약 검토용 소비 요구**다. 실제 API·JSON 스키마·필수 필드·오류 코드가 확정된 것은 아니다. [사용자 인터뷰](overview.md)에 따라 PC 중심, 예제 선택과 직접 입력·업로드를 모두 준비하며 공개 자료만 허용한다. 개별 결과는 공개 목록 없이 본인만 임시 조회·다운로드한다.

후속 사용자 요청으로 [임시 규격 v0.1.0](temporary-contract.md)을 작성했다. 아래 공동 검토 항목이 모두 해결되기를 기다리지 않고 이 규격과 모의 응답으로 서비스 작업을 진행한다. 이 문서는 소비 요구의 배경이며 정확한 임시 필드·타입·enum은 새 규격을 따른다.

## 1. 화면별로 필요한 정보

| 화면·기능 | 사용자가 하는 일 | 로직·서비스에서 받을 정보 | 비어 있거나 실패할 때 |
|---|---|---|---|
| 입력 — F01 | 예제 선택 또는 HER2·후보·자료 입력 | 예제 출처·분석 범위, 후보 식별, 필수/선택 항목, 허용 형식 | 예제 미선정과 네트워크 실패를 구분. 임의 후보를 정식 예제로 표시하지 않음 |
| 입력 확인 — F02 | 서열·파일·분석 대상 확인 | 후보별 오류 위치·이유, 파일↔사슬·구간 대응, 누락 정보 | 수정할 대상을 표시하고 해당 입력으로 비교를 계속하지 않음 |
| 진행 — F03·F04 | 실행 위치·생략·보류·실패 확인 | 실행 ID·상태·현재 단계, 후보별 진행, 단계 이유, 결과 가용 여부 | 통신 단절과 서버 작업 실패를 분리. 근거 없는 완료율·남은 시간 표시 금지 |
| 비교 — F05–F07 | 후보·조건·구조 선택, 근거와 3D 연결 | 구조 파일 참조·대응표·정렬 정보, 근거별 값·단위·종류·잔기 위치 | 좌표 없음·파일 없음·viewer 오류를 구분. 표·보고서는 가능한 범위에서 유지 |
| 보고 — F08·F09 | 의견·후속 질문·출처 확인, 다운로드 | 적용 범위·근거 ID·상충 근거·한계, 결과 버전·파일 참조 | 설명 실패와 계산 실패를 분리하고 실제 완성된 산출물만 제공 |
| 부분 결과 — F10 | 남은 비교와 실패 범위 확인 | 유효 후보·산출물, 실패 후보·단계, 전체 비교 완료 여부 | 한 후보 오류로 다른 결과를 숨기거나 일부 성공을 전체 완료로 표시하지 않음 |

근거: [PRD F01–F10·화면 구성](../PRD.md). 예제와 직접 입력을 같은 내부 입력 기준으로 검증할지, 예제 선택 시 새 분석을 실행할지·저장된 실행을 보여줄지는 계약 검토 사항이다. 저장된 실행을 현재 실행인 것처럼 표시하지 않는다.

## 2. ID와 데이터가 연결되는 단위

아래는 [ARCHITECTURE 데이터 모델](../ARCHITECTURE.md)의 정보를 화면 소비 단위로 정리한 표다. 타입은 **검토할 값의 종류**이며 프로그래밍 언어 타입 선언이 아니다.

| 단위 | 필요한 정보·값의 종류 | 연결 대상과 확인 목적 |
|---|---|---|
| 검토 입력 | 입력 식별자, HER2 식별자/서열, 후보 목록, 형식·구간, 원본 파일 참조·해시·시각 | 수정 전후 입력을 구분하고 분석한 원본을 확인 |
| 후보 | 후보 식별자·표시 이름, 중쇄·경쇄 서열과 범위, 선택 자료 참조 | 이름이 같아도 다른 후보를 구별. 배열의 첫 번째라는 이유만으로 대응하지 않음 |
| 실행 | 실행·입력 식별자, 실행 상태·현재 단계, 설정 버전, 시작·종료·갱신 시각, 오류·결과 존재 여부 | 새 실행과 이전 결과, 서버 상태와 화면 갱신 시점을 구분 |
| 단계·후보 진행 | 소속 실행·후보, 단계명, 실행/생략/보류/실패 의미, 이유·관련 근거 | 예정 단계 수가 다른 분기에서도 실제 진행을 설명. 세부 enum은 미정 |
| 구조 | 구조 식별자, 후보·출처·실험/예측 구분, 파일 참조·형식·해시, model·assembly·구성요소 | viewer가 읽는 파일과 분석한 구조를 일치시킴 |
| 구조 조건 | 조건 식별자, 후보·구조 참조, 포함 성분, 자료 공백·조건 근거 | 같은 후보의 중심/주변 구조 조건을 독립적으로 비교 |
| 잔기 대응 | 구조·model·사슬 author/label ID, 잔기 author/label 번호·삽입 코드, 원서열 위치, 좌표 유무 | 근거표에서 정확한 3D 위치를 선택. 번호 하나로 식별하지 않음 |
| 근거·지표 | 근거 식별자·종류, 후보·조건·구조 참조, 항목명, 숫자 또는 미확인, 단위·정의·설정, 위치·출처·미확인 이유 | 실제 0과 계산 안 됨을 구분하고 계산 조건을 설명 |
| 검토 의견 | 후보·조건·판단 항목, 의견, 근거 참조 목록, 상충 이유·한계·후속 질문 | 하나의 후보라도 항목마다 다른 판단을 표현 |
| 결과 스냅샷 | 실행 식별자·schema version·생성 시각, 근거·의견·산출물 참조 | 화면·보고서·JSON·CSV가 동일한 결과를 사용 |
| 파일 산출물 | 파일 식별자·역할·형식·해시, 실제 가용 상태와 조회 권한 | 서버 경로 대신 승인된 파일 조회로 연결. 미완성 파일을 정상 다운로드로 제공하지 않음 |
| 임시 세션·삭제 — 후속 검토 | 실행·파일 접근 권한, 만료 예정 시각, 조회 가능/만료/정리 중의 의미 | 만료를 분석 실패와 구분. 세션 인증·토큰·정리 상태의 구체적 규격은 미정 |

ID 형식, nullable 여부, 목록 순서, 날짜 직렬화, 조건·구조의 정확한 관계 수, 필드명은 G1에서 정한다. API 공급자가 제공하지 않는 값을 이 표 때문에 새로 만들어 채우지 않는다.

## 3. 지표를 표시하기 전에 받아야 할 것

| 비교 항목 | 로직 담당에게 받을 내용 | 프런트가 임의로 결정하면 안 되는 것 |
|---|---|---|
| 접촉 | 두 대상·참조 잔기/원자, 계산 정의·거리 기준·단위, 실제 결과 | 접촉 개수를 후보 우수성 점수로 변환 |
| 표면 노출 | 사용 구조·성분, 계산 방법·단위·정규화 여부, 미지원·누락 처리 | 다른 범위에서 나온 값의 직접 순위화 |
| 충돌 | 충돌 대상·위치, 판정 기준·제외 규칙, 사용 설정 | 임의 거리 기준으로 viewer에서 새 판정 |
| 구조 신뢰도 | 실제 반환된 지표명·범위·구조 대응·출처·해석 범위 | 신뢰도를 실제 결합 확률로 표시하거나 없는 지표 채움 |
| 자세 일관성 | 비교 구조들·정렬 기준·분석 구간·변환, 지표 정의·단위 | 각 파일의 원래 좌표를 겹친 것만으로 일관성 판단 |
| 주변 구조의 영향 | 조건별 포함 성분·자료 공백·달라진 근거·위치 | 당쇄 좌표 일부를 전체 세포 환경으로 설명 |

과학적 정의·임계값은 [PRD Q05](../PRD.md)의 검토 대상이다. 화면은 단위와 근거를 표시할 수 있도록 준비하되 `null`을 0으로 바꾸거나 공통 100점 척도를 도입하지 않는다.

## 4. 실행 상태·판단·브라우저 상태의 분리

[ARCHITECTURE](../ARCHITECTURE.md)의 **작업 실행 상태 초안**을 그대로 기준으로 삼는다.

| 상태 | 화면에서 읽을 의미 | 함께 필요한 정보 |
|---|---|---|
| `queued` | 접수·저장 후 worker 대기 | 접수 시각·실행 식별자. 대기 순번은 서버가 제공하기 전 표시하지 않음 |
| `running` | worker가 실행 중 | 현재 단계·후보·갱신 시각·단계별 이유 |
| `completed` | 계획한 검토와 결과 저장이 끝남 | 검토 의견·보류 범위. 모두 긍정 판정이라는 뜻이 아님 |
| `partial` | 실행 실패로 일부 예정 산출물 미완료 | 사용할 수 있는 결과와 생성하지 못한 결과 |
| `failed` | 유효한 검토 결과를 만들지 못함 | 입력/실행 실패 구분·실패 단계·이유 |
| `interrupted` | worker 중단 등으로 완료 여부 확인 필요 | 마지막 단계·기존 요청/산출물 확인 상태. 즉시 재실행을 성공 경로로 약속하지 않음 |

검토 의견은 **후속 실험 검토 가능 / 추가 확인 / 보류**이며 후보·조건·판단 항목에 적용한다. `completed` 실행 안의 접근성 보류와 `partial` 실행 안의 성공한 접촉 계산은 둘 다 표현할 수 있어야 한다.

브라우저의 조회 실패·오프라인·3D 로딩 오류는 별도 화면 상태다. 상태 조회가 실패했다고 서버 실행을 `failed`로 바꾸지 않는다. 알려진 마지막 상태를 최신 상태처럼 표시하지 않으며, polling 간격·중단 후 조회 방식은 운영 계약에서 정한다.

자료 부족, 해당 조건에 적용되지 않음, 아직 실행하지 않음, 외부 호출 실패는 서로 다른 이유다. 현재 `null + 이유`라는 설계만 있으므로 이들을 표현할 구체적인 코드·필드와 작업 상태 집계는 공동 검토해야 한다.

## 5. Mol* 연결에 필요한 구조 계약

Mol* 공식 문서는 사슬·잔기 쿼리, 선택·강조, 선택 이벤트의 React 연동을 설명한다. 따라서 표→3D 연결의 구현 경로는 있지만, 우리 파일·잔기 대응으로의 성공은 별도 실험이 필요하다. [Mol* selections](https://molstar.org/docs/plugin/selections/)

| 전달할 항목 | 로직 담당의 확인 | 프런트 확인 |
|---|---|---|
| 표시할 구조 | 분석에 사용한 파일, 실험/예측 종류, model·assembly·사슬 조합 | 같은 파일·대상을 로드하고 후보 전환 시 이전 선택 제거 |
| 잔기 식별 | author/label 번호·삽입 코드·원서열 위치 대응, 좌표 없는 구간 | 번호 체계를 명시해 선택하며 좌표 없는 곳을 임의 강조하지 않음 |
| 복제된 구조 단위 | assembly에서 생기는 사슬 복제와 대응이 필요한지 | 같은 사슬 이름이 여러 공간 단위를 가리킬 때 모호한 선택 방지 |
| 정렬 | 기준 구조·사슬·구간, 변환 행렬과 적용 여부·좌표 단위 | 이미 변환된 파일에 재적용하지 않고 표와 동일한 기준 사용 |
| 접촉·충돌 표시 | 근거와 연결된 잔기/원자 집합·대상 구조 | UI의 선택·강조를 계산 결과와 연결 |
| 당쇄·주변 구조 | 실제 포함된 성분·분석 포함 여부·누락 정보 | 보이기/숨기기를 다른 조건의 재계산 결과로 오해시키지 않음 |

Mol*에는 구조 중첩 기능도 있지만, 프로젝트는 서버가 기록한 정렬 기준·변환을 사용하도록 설계했다. viewer의 자동 정렬을 분석 근거로 삼으려면 로직 담당과 별도로 검토해야 한다. [Mol* superposition](https://molstar.org/docs/plugin/superposition/), [기존 책임 분리](../ARCHITECTURE.md)

특히 [실제 공개 구조 조사](agent-logic.md)의 사슬 이름을 모든 후보에 일반화하지 않는다. 전체 구조의 파일명·PDB ID만 받으면 위의 대응 정보를 복원했다고 보장할 수 없다.

## 6. API와 로직 인계에서 먼저 합의할 것

기존 API 경로 `POST /api/reviews`, `POST /api/reviews/{id}/runs`, `GET /api/runs/{id}`, `GET /api/runs/{id}/result`, `GET /api/artifacts/{id}`는 [ARCHITECTURE의 제안](../ARCHITECTURE.md)이다. 아직 서버가 없으므로 요청·응답 예시나 구현된 엔드포인트로 부르지 않는다.

| 검토 항목 | 합의할 질문 | 담당 경계 |
|---|---|---|
| 접수 형식 | 파일과 후보 메타데이터를 어떻게 묶고 오류 위치를 반환하는가? | 서비스 ↔ 자료·분석 담당 |
| 실행 진입 | 입력·설정 참조를 받는 진입점, 동기/비동기 함수와 실행 수명은 무엇인가? | 서비스 worker 운영부 ↔ 워크플로우 실행부 |
| 진행 인계 | 후보·단계별 이벤트를 언제 보내고 누가 DB에 기록하는가? | 워크플로우가 의미 전달, 서비스의 저장 책임은 공동 확정 |
| 종료·부분 결과 | 계획적 생략/보류, 실패, 설명 실패를 전체 상태에 어떻게 집계하는가? | 로직·서비스 공동 |
| 파일 인계 | 파일을 완성한 시점·경로/참조·해시·소유권을 어떻게 전달하는가? | 로직·서비스 공동 |
| 재실행·중복 | 입력 재접수와 같은 요청의 재전송을 어떻게 구분하는가? | API·worker 운영부 ↔ 외부 호출 실행부 |
| 보관·접근 | 사용자별 임시 결과 권한, 만료 시점·삭제 상태·복구 범위는 무엇인가? | 사용자 정책 확인 후 서비스가 계약 제시 |

FastAPI는 파일과 form을 함께 받는 경우 multipart를 사용한다. 같은 요청을 별도 JSON body와 파일 업로드가 동시에 되는 형식으로 설계하면 안 되므로, form 안에 메타데이터를 넣는 방식과 업로드 분리 방식 중 계약을 정해야 한다. [FastAPI 파일·form](https://fastapi.tiangolo.com/tutorial/request-forms-and-files/)

## 7. 로직 완성 전 준비와 검증

**지금 준비할 수 있는 범위:** 네 화면의 흐름·선택 상태·빈 상태·로딩·오류 표현, 공개 구조 로딩 실험, 위 표를 바탕으로 한 소비 요구 검토. 최종 스키마는 생산자 검토 뒤 고정한다.

합의 후 개발용 모의 응답은 정상·계획적 생략·과학적 보류·부분 실패·통신 단절·viewer 오류를 다루고 항상 모의 데이터라고 표시한다. 계산 전의 과학적 값은 미확인으로 둔다. 공개 구조 메타데이터를 사용하더라도 실제 계산 결과라고 표시하지 않는다.

연결 검증은 (1) 같은 실행·후보·조건의 표→실제 잔기 강조, (2) 새로고침 후 중복 실행 없이 상태 복구, (3) 실패 후보와 다른 후보의 유효 결과 공존, (4) 화면·JSON·CSV의 ID·값·이유 일치로 확인한다. 임시 결과는 허용 기간 내 복구와 만료 후 접근 불가를 따로 검증한다. [삭제·종료 초기안](hosting-requirements.md)에 따라 30분 유예는 잠정값이고, 실행 상태와 접근 만료·삭제 상태를 혼합하지 않는다.
