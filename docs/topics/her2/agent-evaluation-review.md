# 에이전트 평가를 위한 현재 구현 리뷰와 조사 방향

검토일: 2026-09-27. 기준 커밋: `7c5cf2dfcaf2e9be5f10f1da7ea57e89fd3a8f48`.
원격 main을 fetch한 뒤 별도 worktree의 `docs/agent-evaluation`에서 검토했다. 다른 세션의 `feat/her2-direct-input` 미커밋 변경은 포함하지 않았다.

후속 적용: 사용자 요청에 맞춰 범위를 줄인 [해커톤용 평가 기준·데이터](hackathon-evaluation.md)를 작성했다. 아래는 상세 리뷰 시점의 기록이며, 실제 사용할 최소 루브릭·사례·채점 절차는 후속 문서를 따른다.

## 1. 결론과 이번 범위

현재 구현에는 상태별 도구 관문·후보별 세션·중복 예측 방지·장애 후 규칙 복구·출력 스키마 검증이 있다. 그러나 **실행 완료와 결과의 타당성을 구별하는 독립 평가가 충분하지 않다.** 실제로 기존 회귀검사가 통과한 상태에서 잘못된 표적 대응, 근거 없는 설명, 예측 파일과 접촉 근거의 불일치를 재현했다.

평가의 목적은 “모델이 답을 내는가”보다 **올바른 입력·구조·조건에 근거하여 필요한 행동을 하고, 판단할 수 없는 부분을 정확히 남기는가**로 잡는다. 사용자 요청에 따라 입력부터 최종 보고까지 넓게 검토하고 프로젝트에 필요한 우선순위를 제안한다. 제품의 판정 의미와 비용·전문가 검토 조건은 확정 답변 없이 채우지 않는다.

이번 산출물은 현재 상태 리뷰·재현 근거·평가 요구사항·후속 조사 방향이다. 평가 제품, 신뢰성 인증을 마친 데이터셋, 실제 모델 성능 측정이 완성됐다는 의미는 아니다. 제품 로직은 수정하지 않았다.

## 2. 실제 실행 구조

| 층 | 현재 동작 | 평가 시 구별할 사항 |
|---|---|---|
| 영속 서비스 | `service/live.py` → 별도 `logic.run` 프로세스 → 결과·파일 검증 | 접수·저장·소유권·프로세스 실패와 분석 판단의 정답은 별개 |
| 후보별 에이전트 | `Flow.run`이 후보마다 NAT 또는 기존 경로 실행 | 후보 하나의 완료와 2–3개 후보의 일관된 비교를 각각 검사 |
| NAT | Nemotron tool-calling, 도구 7개, YAML의 반복 제한·빈 응답 재시도 | 올바른 도구 순서뿐 아니라 필요성·인자·중단 이유를 검사 |
| 도구 관문 | `CandidateSession` 상태로 허용 도구를 제한하고 락으로 동시 중복 실행 방지 | 거부된 잘못된 시도와 실제로 실행된 잘못된 행동을 구별 |
| 구조 확보 | 로컬 1N8Z·1S78 카탈로그와 항체 중쇄·경쇄 정확 일치, 아니면 예측 또는 보류 | 일반 RCSB 검색기가 아니다. 로컬 검색 실패는 공개 자료 부재의 증거가 아님 |
| 구조 분석 | 실험 구조의 저장 접촉 선택 또는 예측 좌표의 접촉 계산 | 온라인 경로의 충돌·표면 노출은 `not_run`; 정렬·잔기 대응은 미연결 |
| 의견 | `reviewable`/`needs_confirmation`, 근거 ID·한계·후속 질문 기록 | 완료 상태는 과학적 타당성·실험 효용을 보장하지 않음 |
| 복구 | NAT가 끝내지 못하면 현재 세션부터 `RuleDecider`로 이어서 실행 | 모델 단독 성공, 규칙 복구 성공, 전체 실패를 별도 집계 |

근거: [flow.py](../../../logic/flow.py), [agent_session.py](../../../logic/agent_session.py), [nat_agent.py](../../../logic/nat_agent.py), [nat_workflow.yml](../../../logic/nat_workflow.yml), [서비스 경계](../../../service/live.py).

`LOGIC_AGENT_MODE=rule` 자체는 모델 미사용을 뜻하지 않는다. `Flow`의 기본 판단기는 `Decider`이며 이 경로에서도 모델을 호출한다. 모델 없는 기준선에는 명시적인 `RuleDecider`나 통제된 대역이 필요하다. 테스트의 root `conftest.py`는 rule 고정과 자격증명 차단을 함께 적용한다.

A-01/A-02/A-03에는 출처 고정·잔기 대응·SASA·관측 당 비교를 수행하는 별도 오프라인 코드와 결과가 있다. “계산 코드가 없다”와 “서비스 에이전트에 연결되지 않았다”를 혼동하면 안 된다. 이번에는 그 전체 재계산을 수행하지 않았다. [A-02](assets/a02/README.md), [A-03](assets/a03/README.md).

## 3. 실행으로 재현한 우선 문제

모두 실제 모델 대신 `CandidateTools`와 기존 `ScriptedClient`를 직접 호출한 오프라인 경계 검사다. **모델이 이런 답을 실제로 생성했다거나 발생률이 이렇다는 주장은 아니다.** 저장 문구에 모델 이름이 붙는 것 역시 현행 코드의 표기이며 실호출 증거가 아니다.

재현 코드: [probe.py](assets/agent-evaluation-review/probe.py). 결과: [observed.json](assets/agent-evaluation-review/observed.json).

| 우선순위 | 재현 조건 → 실제 결과 | 평가에 필요한 검사 |
|---|---|---|
| P1: 표적 대응 | trastuzumab 사슬은 그대로, 표적은 합성 `A` 607자로 변경 → 입력 통과·1N8Z 완전 일치·실험 구조 선택 허용 | identifier·입력 서열·구조 표적·분석 구간의 대응. 불일치는 재사용 금지 또는 명시 보류 |
| P1: 근거 혼합 | 공개 구조와 일치하는 후보에서 새 예측을 선택하고 좌표 없는 대역 응답을 반환 → `predicted` 구조에 접촉 39개·출처 1N8Z 기록 | 근거의 파일 해시·구조 ID·계산 조건이 실제 분석 대상과 같은지 |
| P1: 설명 의미 | `치료 효능이 입증되었고 부작용이 없다.` → `reviewable` 의견으로 저장 | 근거 밖의 효능·안전성 단정, 누락을 부재로 바꾸는 설명 차단 |
| P1: 값의 의미 | 확인된 접촉 수 39를 `결합 친화도는 39 nM이다.`로 제출 → 저장 | 숫자뿐 아니라 측정항목·단위·대상·조건·출처 결합 검증 |
| P2: 예측 산출물 | 미일치 후보에 `data_x`뿐인 대역 mmCIF → 접촉 `not_run`, 후보 `completed` | HTTP 성공·파일 생성·파싱 가능·사슬 대응·분석 가능·업무 완료를 분리 |
| P1: 평가기 결측 처리 | `ACD`→`AED` 대응에서 접촉 위치 `{1,2,3}` → 미대응 2를 버리고 `{1,3}`만 채점해 F1=1 | 대응 범위·제외 잔기·결측 이유를 별도 출력하고 충분한 대응 전에는 품질점수 해석 보류 |

원인 위치:

- `logic/structures.py:216`의 `find_structure`는 항체 두 사슬만 인자로 받는다. `logic/flow.py:253`은 표적 문자를 검사하지만 실제 표적 동일성을 입증하지 않는다.
- `logic/flow.py:678`의 `_compare`가 선택된 구조 종류보다 `match.complete`로 계산 분기를 고른다. 예측을 선택해도 기존 실험 구조의 접촉을 붙일 수 있다.
- `logic/agent_session.py:127`의 `_check_reason`은 빈 문장·미지 숫자를 검사한다. 확인된 수치를 다른 항목·단위에 붙이거나 숫자 없는 과학적 단정을 하는 경우를 검증하지 않는다.
- `logic/flow.py:567`의 `_record_predicted`는 첫 구조를 저장하며 사슬 매핑이 없을 때 기록을 무효화하지 않는다. `completed`의 의미는 제품 정책과 함께 정해야 한다.
- `assets/goldset/score_epitope.py:33`의 `remap`은 일치 블록만 보존한다. 위 합성 예시는 평가기의 정보 유실을 재현한 것이며, 기존 실제 F1이 모두 틀렸다는 주장은 아니다.

이 문제들은 평가 사례의 출발점이다. 별도 세션의 수정과 충돌하지 않도록 이번 작업에서 제품 코드를 고치지 않았다.

## 4. 설계 대비 아직 평가할 수 없는 부분

입력 `uploads`와 분석 구간을 일반적인 분석 대상으로 소비하는 흐름은 현재 `logic/flow.py`에서 확인되지 않는다. 중쇄·경쇄 구간은 경계 검사가 있지만 실제 조회·예측은 전체 서열을 사용한다. 표적 구간, 업로드 구조 우선 선택, 다중 예측 자세 비교는 각각 기능 지원 여부부터 분리해 기록해야 한다.

현재 `_report`의 `conflicting_evidence_ids`는 빈 목록이며 후속 질문은 고정 문구 중심이다. 따라서 “지표 충돌을 적절히 설명하는가”, “새 후보에 적합한 다음 실험 질문을 만드는가”는 지금의 정상 예제만으로 측정되지 않는다. 비교 화면 존재와 후보 간 과학적 종합 판단을 구별해야 한다.

`overview.md`·`validation.md`의 일부 구현 상태는 현재 코드보다 오래됐다. 이 문서에서는 설계 의도와 코드·현재 실행 결과를 나누어 읽었으며 기존 설계 문서를 일괄 수정하지 않았다.

| `score_epitope.py` | 접촉 잔기 집합의 P/R/F1 탐색 | 자세 전체·항체 방향·사슬 정합성·친화도·접근성 정확도 |

### 기존 goldset에서 먼저 수정할 평가 해석

1. **정답을 도구 설명만으로 만들 수 없다.** 전부 `predict_structure`인 사례는 한 정책의 좁은 준수 검사이며, 항상 예측하는 에이전트도 만점을 얻는다. 올바른 재사용·보류·입력 거절·복구 사례를 함께 구성해야 한다.
2. **HER3 구조는 HER2 비결합의 정답이 아니다.** [4P59](https://www.rcsb.org/structure/4P59)와 [8YRY](https://www.rcsb.org/structure/8YRY)는 공식 entry에서 HER3 복합체다. 현재 채점 코드는 두 항체도 공통 HER2 표적에 넣고 정답을 예측으로 둔다. 이 자료는 알려진 표적·출처 불일치 검사에는 쓸 수 있지만 HER2 비결합 실험 정답으로 승격할 근거는 아직 없다.
3. **서로 다른 항체의 접촉 F1은 정확도 상한이 아니다.** 6BGT 대 1N8Z의 0.923은 해당 두 구조·조건 사이의 겹침 관측이다. 동일 후보의 예측을 동일 후보의 기준 구조와 비교하는 정확도 상한으로 확정할 수 없다. 기존 README의 “천장” 표현을 새 평가 설계에 승계하지 않는다.
4. **자료를 보고 선택한 뒤 시험셋이라고 부르지 않는다.** 기존 10건은 탐색·채점기 검산에 사용됐다. 개발셋으로 관리하고, 최종 시험은 항체 계열·유사 서열·동일 논문/구조군·표적 construct의 중복을 검토해 분리해야 한다. 모델 학습자료 포함 여부는 공개 정보로 확인되는 범위만 기록한다.
5. **조건부 정확도와 실행 가용성의 분모를 분리한다.** 저장 JSONL은 7줄, 현재 `reached_fork=true` 3줄이며 기존 집계는 3/3을 출력한다. 1줄은 이 필드가 없는 구버전이고 6줄에는 규칙 복구가 표시된다. 이는 10개 구조 전체 성공률이 아니다. 데이터 스키마 버전과 시도·도달·복구·오류 건수를 보존해야 한다.

`fetch_cif.sh`는 현재 URL에서 다시 받거나 크기가 있는 파일을 그대로 사용한다. goldset에는 A-01과 같은 버전·해시 검증 절차가 아직 없다. 원본 수집일·entry version·SHA256·역할 대응 근거·라이선스/재배포 조건을 고정해야 재현 가능한 데이터로 쓸 수 있다.

`score_epitope.py`의 7개 예시는 현재 저장 집합의 점수를 출력하며 기대값을 assert하는 자동 시험이 아니다. 이번 출력은 기존 표와 일치했지만 원본 10건 재다운로드·구조 계산·독립 정답 검수는 수행하지 않았다.

빈 응답 뒤 429를 관측한 기록은 보존할 가치가 있다. 그러나 시간적으로 연속됐다는 사실만으로 원인이 한도라고 확정할 수는 없다. 단일 샘플·단일 후보의 예측 개선 역시 일반 성능 향상이나 캐시·세션 원인의 증거로 확대하지 않는다.

## 6. 프로젝트에 제안하는 평가 범위

하나의 종합 점수로 합치지 않고 아래 층별 실패와 근거를 보여준다. 우선순위와 판정 규칙은 제안이며 아직 운영 합격 계약이 아니다.

| 평가층 | 핵심 질문 | 기준 자료·지표 |
|---|---|---|
| 입력·대응 | 입력과 실제 분석 대상이 같은가? | 표적/항체/구간/assembly/chain/잔기 정합, 금지 재사용 건수 |
| 도구 선택 | 현재 자료로 필요한 행동을 했는가? | 허용 행동 집합, 필수 선행조건, 불필요한 예측·반복·부당 보류 |
| 실행·복구 | 실패를 숨기거나 중복 비용을 만들지 않는가? | 완료율, 모델 단독 완료율, 복구율, 실패 사유, 중복 호출, 상태 보존 |
| 계산·구조 | 재현 가능한 올바른 계산인가? | 사슬 대응률, 접촉 P/R/F1, 자세 지표, 계산 오차, 결측 비율 |
| 의견·근거 | 주장마다 올바른 근거와 한계가 있는가? | 주장–근거 대응, 값·단위·조건 일치, 과장·출처 혼동·누락 단정 |
| 결과 전달 | 입력부터 저장·보고·3D까지 같은 결과인가? | 후보/실행/조건/파일 해시 일치, 잔기 강조, 실패·보류 표시 |
| 안정성·효율 | 같은 조건과 동등한 입력에서 일관적인가? | 반복 분포·변동, 후보 순서/이름/FASTA 포맷 불변성, 호출·시간·비용 |
| 연구자 효용 | 판단과 다음 확인에 실제 도움이 되는가? | 전문가의 근거 적절성·빠진 질문 평가, 비교 업무 시간·수정 부담 |

도구 순서 전체를 문자열 하나로 고정하지 않는다. 같은 목적을 달성하는 여러 유효 경로를 허용하되, 검사 전 예측·오류 구조 재사용 같은 금지 행동을 명시한다. 도구가 거부한 위험 시도와 실제 부작용 발생을 함께 기록한다.

일반 문장 품질은 검토 보조에만 LLM 판정기를 쓸 수 있다. 생물학적 정답이나 제품 정책을 동일 모델의 평가에 전적으로 맡기지 않는다. 사람이 채점한 표본으로 판정기 자체의 불일치·과신을 검증한 뒤 적용한다.

## 7. 테스트 데이터 구축 방향

| 묶음 | 포함할 사례 | 정답의 출처 |
|---|---|---|
| 검산·회귀 | 1N8Z·1S78, A-01–03, 이번 재현 6종 | 고정 원본·독립 재계산·논리적으로 정한 합성 조건 |
| 실제 구조 확장 | HER2 항체의 다른 계열·construct·관측 조건 | RCSB entry/논문/validation 보고서와 사슬 검수 |
| 오류·결측 | 잘못된 표적·범위·사슬, 손상 파일, 관측되지 않은 당·잔기 | 합성 변형 이력과 기대 행동의 명시적 정책 |
| 장애·적대 입력 | 429·timeout·빈 응답·부분 성공·동시 도구, 이름/주석에 지시문 삽입 | 통제된 장애 주입과 상태·비용·출처 불변조건 |
| 독립 최종 시험 | 개발에 쓰지 않은 구조군·복합 시나리오 | 검수·동결된 기대 행동과 근거; 불확실한 라벨은 평가 제외 사유 유지 |

사례마다 최소한 `case_id`, 목적·태그, 원본 출처와 해시, 입력·정답 근거, 허용/금지 행동, 기대 상태, 비교 허용오차, 결측·적용 불가 조건, 검수자/검수 상태, 분할 그룹, 라벨·데이터 버전을 남긴다. 모델이 본 입력과 평가기만 볼 기준 구조도 구분한다.

구조를 지우고 같은 구조를 복원하는 과제, 공개 구조 검색·재사용 과제, 근거 보고 과제는 입력 공개 범위가 다르다. 기준 구조를 에이전트에게 보여주면서 독립 예측 정확도로 계산하지 않는다. 양성만 많은 데이터에서 항상 예측·항상 보류하는 단순 기준선의 점수도 확인한다.

외부 데이터 상세 조사는 **RCSB 구조·검증 보고서를 우선**하고, 항체 특화 탐색 후보로 [SAbDab](https://sabdab.opig.stats.ox.ac.uk/)를 확인한다. SAbDab의 현재 제공 필드·HER2 커버리지·중복 제거·사용 조건은 후속 검증 대상이다. [SKEMPI 2.0](https://life.bsc.es/pid/skempi2/) 같은 실험 변이 자료는 필요성이 확정될 때 별도 검토하며, 현재 HER2 평가에 충분한 자료가 있다고 가정하지 않는다.

## 8. 평가 도구 조사·구현의 방향

| 후보 | 이 프로젝트에서 맡길 역할 | 선택 전 검증할 조건 |
|---|---|---|
| 기존 pytest + 독립 평가 함수 | 스키마·상태·금지 행동·수치·참조 관계의 결정론적 판정 | 제품 코드를 정답 생성기로 그대로 사용하지 않는지, 알려진 오류를 잡는지 |
| NAT custom evaluator | 실제 workflow 입력/출력/도구 경로의 반복 실행·수집 | 현재 1.9.0과 문서 API 호환성, 실패 기록 보존, 비용·병렬 한도, 재생 가능성 |
| DockQ 계열 구조 평가 | 접촉 집합 점수를 보완하는 자세·인터페이스 비교 | HER2–Fab 다중 사슬 대응, 기준 construct·평가 구간·결측, 독립 실행 재현 |

NVIDIA 공식 문서는 custom evaluator의 출력·기대값·trajectory 접근과 등록 확장을 설명한다. 현재 lock 환경은 `nvidia-nat`와 `nvidia-nat-eval` 1.9.0이며, 조회한 문서 페이지의 표시 버전은 1.8이었다. **설치되어 있다는 사실과 우리 Flow를 평가 가능하게 연결했다는 사실은 다르다.** [NAT 공식 문서](https://docs.nvidia.com/nemo/agent-toolkit/latest/extend/custom-components/custom-evaluator.html).

DockQ 공식 구현은 인터페이스별 DockQ·iRMSD·LRMSD·접촉 지표와 사슬 대응 기능을 제공한다. 우리 접촉 잔기 F1과 정의가 같다고 가정하지 않고 따로 기록하며, 친화도나 효능 점수로 사용하지 않는다. 이번에는 설치·실행·임계값 채택을 하지 않았다. [DockQ 공식 저장소](https://github.com/wallnerlab/DockQ).

다음 상세 비교에서는 유지관리·버전 고정·라이선스·자체 호스팅/비용·원본 trace 보존·오류 시 분모 유지·사용자 정의 평가·평가기 자체 검증을 기준으로 도구를 비교한다. 범용 QA 벤치마크의 점수를 HER2 업무 정답률로 대체하지 않는다.

현재 `session.calls`에는 도구명·허용 여부 중심의 정보가 있고 `logic.run`은 `flow.agent_traces`와 `decider.decisions`를 결과 파일로 직렬화하지 않는다. `measure_agent`의 임시 폴더도 종료 시 사라진다. 평가 실행에는 입력/출력 원본, 도구 인자·결과, 실행 주체, fallback 사유, 오류, 모델·프롬프트·도구·데이터 버전/해시, 사용량·시간을 남기는 별도 저장이 필요하다. NAT의 실제 LLM 경로는 `NvidiaClient.chat`과 다르므로 두 로그가 동일하다고 가정하지 않는다.

## 9. 진행 순서와 완료 조건

1. **평가 계약**: 판정 단위와 `reviewable`/`needs_confirmation`/`hold`의 의미, 필수 근거, 지원 범위를 정한다. 완료 조건은 각 사례에 허용·금지 행동과 보류 이유의 근거가 있는 것이다.
2. **데이터·평가기 검수**: 기존 goldset을 개발용으로 재분류하고 출처·정답·분할을 검수한다. 이번 재현 문제를 잡는 오프라인 평가부터 만든다. 완료 조건은 정상 대조를 통과하고 의도적으로 넣은 잘못된 결과를 구별하는 것이다.
3. **실행·추적 연결**: 순수 규칙 기준선, 고정 도구 응답을 쓰는 실제 에이전트, 실제 구조 도구까지 쓰는 전체 실행을 분리한다. 완료 조건은 동일 case/version으로 결과와 실패 이유를 다시 추적할 수 있는 것이다.
4. **실제 반복·통합 평가**: 비용·호출 한도에 맞춰 반복하고 오류·복구를 포함한 분모를 보고한다. 새 데이터의 성능은 개발셋 점수와 분리한다. 서비스·3D·보고서 연결도 별도 확인한다.
5. **연구자 검토**: 전문가 접근이 확보되면 근거와 후속 질문의 유용성을 평가한다. 확보되지 않으면 이 축은 미검증으로 유지한다.

현재 제안은 P1 의미 오류를 필수 실패 항목으로 삼고, 수치 정확도·모델 성공률·시간은 층별 분포로 제시하는 것이다. 합격 퍼센트·허용 시간·표본 수를 근거 없이 확정하지 않는다. 다른 세션 변경이 main에 반영되면 그 커밋을 새 기준으로 동일 사례를 다시 검토한다.

사용자가 확인한 판정 단위는 **검토 주제별**이다. 따라서 이후 평가 정답은 후보·조건·주제별로 구성한다. 접촉 부위에 충분한 근거가 있으면 그 주제는 검토 가능하되, 미계산 접근성·당쇄 영향은 별도 보류한다. 필수 검증을 통과하지 못한 표적·구조의 접촉은 단순히 값이 있다는 이유로 검토 가능으로 인정하지 않는다. 현재 계약의 topic/decision 표현과 화면 집계에 이 구분을 연결하는 작업은 후속 구현 대상이다.

## 10. 인터뷰 상태

확인된 사용자 결정: 평가 범위는 되도록 넓게 잡고, 프로젝트에 필요한 범위·우선순위는 조사 결과를 바탕으로 제안한다. 판정은 검토 주제별로 나누며, 접촉 부위는 검토 가능·접근성 등 미확인 항목은 별도 보류할 수 있다.

아직 답변이 필요한 사항:

- 실제 모델 평가의 비용·호출 한도·완료 시점.
- 바이오 전문가의 정답 검수·연구자 평가 참여 가능 여부.

이 답변이 없어도 코드 리뷰·오프라인 실패 재현·공개 출처 조사·도구 비교는 진행할 수 있다. 실호출 예산과 과학적 합격 라벨은 임의로 확정하지 않는다.
