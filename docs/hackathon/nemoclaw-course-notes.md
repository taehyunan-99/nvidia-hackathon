> 이전 기록: `nvidia/docs/22-nemoclaw-dli-course-notes.md`에서 2026-09-24 이관. 아래 조사·작성 기준일을 유지하며 이번 이관에서 외부 사실이나 실행 결과를 재검증하지 않았습니다.

이 문서는 `nvidia2`에서 2026-09-20 전후 작성한 강의 페이지 학습 노트를 옮긴 것이다. 아래의 실습 결과 설명은 강의 예시를 해석한 내용이며, 이 저장소에서 API 호출·NemoClaw 환경 실행·수료를 검증했다는 뜻은 아니다. 링크와 실행 조건은 실제 학습 시 다시 확인한다.

출처: [공식 강의 홈](https://nvdli.github.io/NemoClawDLI/nemoclaw/index.html). 이 문서는 1a~4c의 개념, 실습 순서, 결과를 해석하는 방법을 강의 페이지에 따라 정리한다. 모듈 3~4의 런타임 실습은 3a에서 NemoClaw 실행 환경을 연결한 뒤 수행한다.

## 강의 진행 방법

1. 강의 홈에서 채팅 모델과 임베딩 모델의 경로를 확인하고 NVIDIA API 키를 설정한다. 모듈 1~2의 브라우저 실습은 이 경로로 모델을 호출한다. 코드 셀과 시각화는 각 강의 페이지에서 실행된다.
2. **1a → 1b → 1c → 2a → 2b → 2c → 3a → 3b → 3c → 4a → 4b → 4c** 순서로 읽는다. 앞의 에이전트 루프와 도구 호출을 이해한 뒤 워크플로·검색·심층 조사, 지속 실행, 정책 경계를 비교할 수 있도록 구성돼 있다.
3. 각 페이지에서 설명을 읽고 `Run` 또는 `Run all`을 누른다. 출력의 모델 응답, 도구 요청, 실행된 도구, 반환된 결과, 최종 답변을 순서대로 확인한다. 대화형 실습은 예시 질문을 선택한 뒤 `Send`로 실행한다.
4. 기본 실행이 끝나면 강의가 제안하는 대로 **입력 한 가지를 바꿔** 다시 실행한다. 예를 들어 질문, 도구 설명, 검색 대상, 대화 기록 토글을 바꾸면 어느 단계의 행동이 달라졌는지 비교할 수 있다.

## 전체 구조

| 단계 | 무엇을 결정하는가 | 무엇을 다음 단계에 넘기는가 |
|---|---|---|
| 에이전트 루프 | 관찰 뒤 다음 행동 또는 종료 | 대화 기록과 관찰 |
| 도구 호출 | 모델이 요청한 함수를 실행할지 | 검증된 도구 결과 |
| 워크플로 | 분류·분기·병렬화·합류 순서 | 단계별 상태와 전문가 결과 |
| Index Agent | 어떤 근거 문단을 가져올지 | 상위 K개 문단으로 제한한 문맥 |
| Deep Agent | 조사를 어떤 독립 과제로 나눌지 | 작업자별 근거·초안과 종합 결과 |

## 1a. 에이전트 루프

[The Agent](https://nvdli.github.io/NemoClawDLI/nemoclaw/01a-loop.html)

- 에이전트는 환경을 **관찰(perception) → 판단(reasoning) → 행동(action)** 하고, 행동으로 바뀐 환경을 다시 관찰한다. 판단 단계에 규칙이나 언어 모델을 넣어도 루프의 경계는 같다.
- 강의의 `chat()` 호출은 요청마다 독립적이다. 대화 기억은 호출 사이에 서버가 보관하는 것이 아니라, 애플리케이션이 이전 `messages`를 다음 요청에 다시 포함하는 방식으로 만든다.
- 모델 응답의 `finish_reason`을 내용과 함께 읽는다. `stop`은 최종 답변, `tool_calls`는 도구 실행 요청, `length`는 토큰 예산 소진을 뜻한다. `reasoning_content`는 모델과 설정에 따라 없을 수 있다.
- 대화 기록 토글 실습에서는 기록을 보낼 때 이전에 알려 준 이름을 답했고, 기록을 빼자 그 이름을 알 수 없다고 답했다. 같은 모델이라도 **요청에 포함된 문맥**이 달라진 결과다.

### 같은 루프에 다른 판단기를 넣기

강의는 에이전트의 **환경 상태**(현재 위치·벽)와 **내부 상태**(진행 방향)를 분리한다. 가장 작은 예시에서는 0과 9 사이의 일차원 길에서 벽을 만나면 방향을 뒤집는 `if` 규칙만으로 25번의 관찰·판단·행동을 반복한다. 언어 모델이 없어도 에이전트 루프는 성립한다.

미로 예시는 동일한 환경 관찰과 이동 절차에 서로 다른 판단기를 넣는다. 항상 동쪽으로 가는 규칙은 막다른 곳에서 멈추고, DFS는 막히면 되돌아가며, BFS는 넓게 탐색해 최단 경로를 찾고, A*는 목표 방향에 가중치를 둔다. 이어지는 언어 모델 예시에서는 **컨트롤러가 방문 기록·되돌아가는 경로·통로 이동을 관리**하고, 모델은 갈림길에서 `choose_direction`으로 다음 방향을 요청한다. 컨트롤러는 도구 이름과 인자를 검증한 뒤에만 실제 이동을 적용한다.

이 예시를 코드 경계로 다시 읽으면 **환경 일부 샘플링 → 시스템 지시·기록·관찰을 요청 문맥으로 구성 → 모델의 이동 의도 수신 → 검증된 이동 적용 → 바뀐 환경을 다시 샘플링**이다. 모델 호출 자체는 미로를 움직이지 않고 상태도 보존하지 않는다. 같은 미로에서 대화 기록 포함 여부, 전략 지시, 모델 프로필을 하나씩 바꾸어 갈림길 선택과 시간을 비교할 수 있다. 모델 프로필은 여러 설정을 함께 바꿀 수 있으므로 차이를 모델 이름 하나로만 설명하지 않는다.

### 실습을 따라가는 방법

1. 규칙 기반의 가장 작은 에이전트 예시에서 환경 관찰값을 읽고 행동을 고르는 위치를 찾는다. 언어 모델이 없어도 관찰·판단·행동 루프는 존재한다.
   `Run all`로 길의 위치가 두 벽 사이를 왕복하는지 확인하고, `state.env`와 `state.agent`가 무엇을 따로 저장하는지 읽는다.
2. **A real call, in your browser**의 단일 `chat()` 셀을 실행한다. 질문 하나와 모델 이름을 보낸 뒤 반환된 `choices[0].message`와 `finish_reason`을 읽는다. 이 셀에는 대화 기록을 갱신하는 루프가 없다.
3. **Try it · compare conversation history**에서 이름을 알려 주고 다시 물어본다. 기록을 끈 뒤 같은 질문을 반복한다. 모델이 갑자기 다른 능력을 갖게 된 것이 아니라, 두 번째 요청에서 이전 메시지가 빠진 것을 확인한다.

핵심 확인 질문은 “모델이 무엇을 기억하는가?”보다 “이번 요청의 `messages`에 무엇이 들어 있는가?”이다. `reasoning_content`가 보이더라도 사용자에게 내보내는 최종 답변은 `content`와 종료 상태를 기준으로 처리한다.

## 1b. ReAct와 도구 호출

[The ReAct Loop](https://nvdli.github.io/NemoClawDLI/nemoclaw/01b-react.html)

- ReAct 루프는 모델의 판단, 도구를 통한 행동, 결과 관찰을 반복한다. 도구의 이름·설명·입력 스키마를 모델에 **제공**하는 일과 실제 함수를 **실행**하는 일은 별개다.
- 모델이 `tool_calls`를 반환하면 실행 코드가 요청 이름과 인자를 확인해 함수를 호출한다. 이후 도구 요청을 담은 assistant 메시지와 결과를 담은 tool 메시지를 대화 기록에 추가하고 모델을 다시 호출한다. `finish_reason: stop`이면 답변을 반환한다.
- 시각 질문 실습에서는 모델이 `get_current_time`을 요청했고, 실행 코드가 현재 UTC 시각을 돌려준 다음 모델이 그 관찰값으로 최종 답변을 만들었다. 도구가 제공돼 있어도 모델은 질문에 따라 호출하지 않을 수 있다.
- 강의의 확장 예시는 LangChain의 `createReactAgent`에 `read_course_page` 도구를 붙인다. 에이전트가 필요한 강의 페이지를 읽고 출처를 붙여 답하는 흐름을 보여 준다.
- 루프의 `messages`가 길어지면 오래된 관찰·모순·나쁜 관례가 함께 남아 다음 판단을 흐릴 수 있다. 강의는 이를 **context rot**으로 설명하고, 긴 문맥의 중간에 묻힌 정보가 덜 활용될 수 있다는 연구를 연결한다. 필요한 근거를 현재 판단 가까이에 두기 위해 미리 계획하거나, 하위 과제에 짧은 문맥을 주거나, 오래된 대화를 요약하는 방법을 소개한다.

### 한 턴의 실행 순서

1. 실행 코드가 시스템 지시, 사용자 질문, 허용된 도구 스키마를 모델에 보낸다.
2. 응답이 `tool_calls`이면 호출 이름과 인자를 읽고 실제 함수가 허용·실행 가능한지 검사한다.
3. 함수를 실행한 결과를 해당 호출 ID와 연결된 `tool` 메시지로 기록한다. 다음 모델 호출에는 앞선 assistant 도구 요청과 tool 결과가 함께 들어간다.
4. 모델이 `stop`으로 끝나면 답변을 반환한다. `length`나 불완전한 응답을 정상 완료로 처리하지 않는다.

### 실습을 따라가는 방법

- 첫 셀은 도구를 **제공하지 않은** 일반 질문과 `get_current_time`을 **제공한** 실시간 질문을 비교한다. 두 번째 응답이 `tool_calls`여도 그 셀은 아직 시계를 실행하지 않았다. 요청한 함수 이름과 `finish_reason`을 확인한다.
- **The complete ReAct loop**의 `Run all`은 사용자 입력 → 도구 등록 → 모델 판단 → 실제 시계 실행 → 관찰 기록 → 최종 답변을 잇는다. 출력의 메시지 배열에서 사용자 질문, assistant 도구 요청, tool 결과, 최종 assistant 답변을 순서대로 읽는다.
- **Applying the Same Loop to the Course**에서는 `read_course_page`를 가진 채팅 에이전트에게 “How does the clock loop decide when to stop?”을 묻는다. 어떤 페이지를 읽었는지 도구 기록과 출처 칩을 열어 답변의 근거를 확인한다.

같은 질문이라도 도구 호출을 강제하지 않으면 모델이 바로 답할 수 있다. 도구가 꼭 필요한 업무라면 프롬프트만 믿지 말고, 결과에 실제 도구 관찰값이 있는지 확인해야 한다.

## 1c. 여러 도구와 MCP

[Tools at Scale](https://nvdli.github.io/NemoClawDLI/nemoclaw/01c-tools.html)

- 도구가 늘어나면 모델은 이름·설명·인자 스키마를 보고 고른다. `calculate`와 `explain_concept`의 용도를 분리한 실습에서 산술 질문은 `calculate`로 라우팅됐다.
- JSON Schema는 모델에 입력 형식을 설명하지만, 반환된 호출의 안전성이나 정확성을 보증하지 않는다. 실행 코드는 도구 이름을 확인하고 인자를 파싱·검증한 뒤 디스패치해야 한다.
- `glossary_search` 실습은 브라우저 안의 MCP 서버에 `tools/call` 요청을 보내 검색 결과를 받아온다. 이어지는 모델 호출은 검색 결과를 근거로 답한다. MCP는 다른 프로세스가 제공하는 도구를 발견하고 호출하는 표준 경계이며, 원격 서버를 연결할 때는 신원·권한 범위·네트워크 대상을 검토한다.
- 복잡한 기능을 하나의 도구 인터페이스 뒤에 둔 **sub-agent as a tool** 패턴은 바깥 에이전트의 도구 목록을 작게 유지한다. 사용자 대화 실습에서는 계산 호출 결과를 받아 최종 답변을 생성했다.

### 하위 에이전트와 MCP의 경계

하위 에이전트를 도구로 감싸면 상위 모델은 `query_customer_db(question)`처럼 **하나의 자연어 질문 도구**만 본다. 하위 에이전트는 자기 문맥에서 표의 스키마와 행을 읽고 답을 돌려준다. 상위 모델에 원본 행을 처음부터 넣지 않아 문맥을 분리하지만, 하위 에이전트의 답에 행 정보가 실릴 수 있다. **문맥 분리는 데이터 접근 제어가 아니며**, 실제 고객 자료라면 질의 권한과 반환 가능 범위를 별도로 검사해야 한다.

MCP 실습은 별도 도구 서버에 대해 클라이언트가 `tools/list`로 목록·설명·입력 스키마를 발견하고, 모델에 그 스키마를 제공한 뒤 선택된 도구를 `tools/call`로 호출한다. 강의는 브라우저 안의 작은 서버로 JSON-RPC 형태를 재현하며, 실제 배포에서는 같은 호출을 stdio 또는 HTTP로 전송할 수 있다고 설명한다. 서버를 발견했다고 바로 신뢰하지 않고 **서버 신원, 제공 기능, 최소 권한, 자격증명의 대상(audience), 원격 연결·리다이렉트 목적지**를 확인해야 한다. 이미 위치와 호출법을 아는 단일 기능에는 로컬 함수·직접 API·저장소 스킬이 더 단순할 수 있다.

### 실습을 따라가는 방법

1. **Two tools, the model routes**에서 같은 질문에 `calculate`와 `explain_concept`를 함께 제공한다. 산술 질문에는 계산 도구, 개념 질문에는 설명 도구가 선택되는지 `routed_to`와 인자를 확인한다. 도구 설명을 바꾸면 경로가 바뀔 수 있다.
2. **Glossary search**의 `Run all`은 질문과 검색 도구의 JSON Schema를 준비하고, 모델이 만든 검색어로 브라우저 안의 MCP 서버에 `tools/call`을 보낸다. 반환된 항목을 다시 모델에 전달해 최종 답변을 만든다. 검색 실행 전의 모델 지식과 검색 결과에 근거한 답변을 구분한다.
3. **Try it · an agent with two real tools**에서는 산술 또는 NVIDIA 용어를 질문한다. 답변 전에 어떤 도구 칩이 표시되는지, 도구 인자가 실제 질문과 맞는지, 최종 답변이 도구 결과와 일치하는지 확인한다.
4. 확장 실습 **Agents as tools**는 고객 표를 아는 하위 에이전트를 `query_customer_db` 하나로 노출한다. 상위 모델의 도구 목록과 하위 모델이 실제로 읽은 자료를 비교하고, 최종 답변이 표의 행으로 뒷받침되는지 검사한다.
5. 확장 실습 **MCP discovery and invocation**은 `tools/list` 결과를 모델 도구 형식으로 변환하고, 모델의 호출 이름·ID·인자를 검증한 뒤 `tools/call`로 디스패치한다. 반환된 텍스트를 tool 메시지로 붙이고 모델을 다시 호출한다. 도구가 직접 함수에서 서버로 옮겨도 ReAct 루프의 요청·실행·관찰 계약은 유지된다.

도구 목록이 커질수록 도구 이름보다 **용도와 경계가 명확한 설명**이 중요하다. 예를 들어 특정 검색 서비스 이름을 도구 이름에 박아 넣기보다 `glossary_search`처럼 기능을 표현하면 실행 백엔드를 바꿔도 바깥 계약을 유지할 수 있다.

## 2a. 워크플로, 라우팅, 병렬 작업

[Workflows](https://nvdli.github.io/NemoClawDLI/nemoclaw/02a-routing.html)

- ReAct가 매 관찰 뒤 다음 행동을 고르는 루프라면, 워크플로는 실행 코드가 모델 호출·결정적 단계·도구·전문가 루프의 연결과 데이터 흐름을 소유한다. ReWOO는 먼저 계획을 만든 뒤 도구 단계를 실행하고 결과를 종합하는 패턴이다.
- 티켓 실습은 모델이 고정된 카테고리와 우선순위를 구조화해 반환하게 한다. 실행 코드는 허용된 카테고리를 검사하고 해당 전문가 프롬프트로 라우팅한다. 예시 VPN 문제는 네트워크 담당으로 분류됐다.
- 병렬 실습은 한 번 검색한 근거를 기술 설명·쉬운 설명·비판 관점의 전문가에게 함께 전달한다. `Promise.all`로 동시에 실행하면 전체 대기 시간은 가장 늦은 작업의 완료에 좌우된다. 여러 전문가를 쓰는 비용과 조정 부담은 답변 품질·지연과 비교해야 한다.
- 비판 역할의 결과도 근거와 대조해야 한다. 공유된 검색 자료가 질문을 충분히 다루지 않으면 전문가를 늘려도 그 빈틈은 남는다.
- ReWOO의 강의 예시는 구조화된 계획에서 **서로 보완적인 용어집 검색어 3~5개**를 만들고, 순수 JavaScript가 이를 병렬 검색한 뒤 모델이 결과를 종합한다. 모델 호출은 계획과 종합의 두 번이며, `Promise.all`은 동시 실행 수단일 뿐 작업을 계획하거나 판단하지 않는다. 기본 `Promise.all`은 한 분기가 실패하면 전체가 거절되므로 분기별 실패 처리는 따로 설계해야 한다.

### 세 패턴의 선택 기준

| 패턴 | 판단 시점 | 적합한 상황 | 확인할 비용 |
|---|---|---|---|
| ReAct | 매 도구 결과를 본 뒤 | 중간 관찰에 따라 다음 행동이 달라짐 | 반복 모델 호출과 길어지는 대화 기록 |
| ReWOO | 먼저 계획하고 이후 실행 | 단계를 미리 정할 수 있음 | 초기 계획이 틀렸을 때의 수정 비용 |
| 분류 후 전문가 라우팅 | 분류 단계에서 경로 선택 | 입력 유형마다 다른 지시나 도구가 필요함 | 분류 오류와 추가 모델 호출 |
| 병렬 전문가 | 독립 과제를 동시에 시작 | 공유 근거로 서로 다른 관점이 필요함 | 호출량, 가장 느린 분기의 지연, 결과 합치기 |

### 실습을 따라가는 방법

1. **Route a ticket to a specialist**에서 티켓을 구조화된 `category`·`priority`·`summary`로 분류한다. 허용 값은 고정된 enum이며, JavaScript 라우터가 카테고리와 전문가 지시를 대응시킨다. 분류 결과만으로 답했다고 생각하지 말고 전문가 단계까지 확인한다.
2. **Fanning one shared input out**은 같은 검색 결과를 세 전문가에게 한 번씩 전달한다. 기술 설명, 비전문가 설명, 비판 결과를 나란히 비교한다. 실행 시간 표시는 병렬 작업의 총 대기 시간이 각 작업 시간의 합이 아니라 가장 늦은 분기에 가깝다는 점을 보여 준다.
3. **Try it · the triage router**에서 지원 질문을 보내 분류 도구 칩과 최종 전문가 답변을 확인한다. 다른 유형의 예시 질문을 선택하면 분류 경로가 바뀐다.
4. 확장 실습 **Run the full plan-execute-synthesize pipeline**에서는 조사 목표를 정하고, 계획자가 JSON 스키마에 맞는 `topic`과 검색어 목록을 내놓게 한다. 실행 단계는 모델을 다시 묻지 않고 각 검색을 병렬로 수행한다. 종합 단계가 검색 번호로 근거를 연결한 짧은 보고서를 만든다. 목표를 바꾸어 계획과 검색 결과가 어떻게 달라지는지 비교한다.

이 단원의 핵심은 에이전트를 여러 개 만드는 자체가 아니라, **어느 단계가 다음 단계를 결정하는지** 실행 코드에서 명확히 하는 것이다. 검색 근거가 질문과 맞지 않으면 병렬로 생성한 답변도 근거가 충분해지지 않는다.

## 2b. Index Agent와 RAG

[The Index Agent](https://nvdli.github.io/NemoClawDLI/nemoclaw/02b-rag.html)

- Index Agent는 자료를 미리 임베딩해 색인하고, 질문을 임베딩해 가까운 문단을 찾은 뒤, **크기가 제한된 근거 묶음**을 모델에 전달한다. 전통적인 RAG는 답변 전에 고정적으로 검색하며, 에이전트 방식은 검색을 도구로 제공해 루프가 추가 조회 여부를 고른다.
- 색인에는 `passage`, 질문에는 `query` 입력 유형을 쓴다. 코사인 유사도로 순위를 매겨 상위 K개 문단을 선택한다. 강의 실습은 8개 문단의 2048차원 벡터 색인을 만들고 ReAct와 ReWOO의 차이를 묻는 질문에서 관련 문단을 상위에 배치했다.
- 색인은 원문과 임베딩 모델의 출력으로 만든 캐시다. 원문이나 임베딩 설정이 바뀌면 기존 벡터의 유효성을 확인하고 다시 색인해야 한다.
- 강의가 고정해 사용하는 임베딩 모델 ID는 `nvidia/nemotron-3-embed-1b`다. 모델 교체, 제공자의 조용한 버전 변경, 서비스 간 다른 모델 ID 사용은 점수의 의미를 바꾸므로 벡터마다 모델 버전을 함께 관리하고 다른 버전의 벡터를 섞지 않아야 한다.
- 대화 실습은 검색된 상위 문단을 근거로 답하고 인용을 붙인다. 관련 문단을 찾는 일과 답변의 각 주장이 그 문단에 의해 뒷받침되는지는 따로 검토해야 한다.

### 어떤 자료를 어떻게 찾는가

| 자료 형태 | 강의가 제시한 검색 단위와 방법 |
|---|---|
| 구조가 약한 일반 문장 | 작은 문단을 임베딩하고 유사도 상위 K개를 가져온다. 이 단원의 기본 구현이다. |
| 제목·절·표가 있는 문서 | 작은 자식 문단을 검색하되 제목 구조, 표 단위, 부모 포인터를 보존하고 적중한 부모 절을 모델에 건넨다. |
| 그림·차트·슬라이드 | 페이지 이미지와 텍스트를 각각 임베딩하는 이중 검색 경로를 쓴다. |
| 관리되는 구조화 표 | 이 강의에서 구현하지 않는다. 행 전체를 직접 노출하는 대신 의미 계층이 검토된 지표만 제공하는 방식을 소개한다. |
| 관계·그래프 데이터 | 그래프 탐색 도구가 명시적인 간선을 가진 부분 그래프를 반환한다. 단순 벡터 검색은 관계를 온전히 전달하지 못할 수 있다. |

짧은 문단은 특정 질문과 잘 맞지만 답에 필요한 주변 문맥을 잃기 쉽고, 긴 문서는 주변 문맥을 담지만 하나의 벡터에 여러 주제가 섞여 적중률이 떨어질 수 있다. 강의의 부모·자식 검색 예시는 **짧은 자식 문단을 색인하고, 적중 시 전체 부모 문서를 반환**해 두 요구를 연결한다.

코퍼스 전체의 주제처럼 답이 한두 문단에 모이지 않는 **전역 질문**에는 상위 K개만 읽는 방식이 적합하지 않다. 강의의 GraphRAG 설명은 색인 시 문서에서 개체·관계를 추출해 그래프를 만들고, 커뮤니티를 찾고, 커뮤니티별 요약을 준비한다. 질의 시 관련 커뮤니티의 부분 답변을 합쳐 전역 답변을 만든다. 강의의 비교 예시는 실제 그래프 추출 대신 사람이 붙인 그룹으로 상위 K 검색과 커뮤니티 요약의 범위 차이를 보여 주며, 그룹·요약 자체도 평가해야 한다.

### 색인과 답변 생성의 분리

| 시점 | 작업 | 산출물 |
|---|---|---|
| 색인 구축 | 문서를 문단으로 나누고 각 문단을 `passage` 유형으로 임베딩 | 원문·벡터의 쌍 |
| 질문 처리 | 질문을 `query` 유형으로 임베딩하고 코사인 유사도 계산 | 점수 순으로 정렬된 후보 |
| 근거 전달 | 상위 K개 원문만 선택해 모델에 전달 | 범위가 제한된 근거 묶음 |
| 답변 검토 | 답변 문장과 인용 문단을 대조 | 근거가 확인된 주장과 부족한 주장 |

### 실습을 따라가는 방법

1. **Inspect one embedding**에서 한 문장이 숫자 벡터로 바뀌는 것을 본다. 첫 16개 차원은 시각화를 위한 일부일 뿐이며, 강의의 해당 임베딩은 전체 2048차원이다.
2. **Build an Index Agent**의 `Run all`은 8개 문단을 임베딩하고 질문 벡터와 각 문단의 코사인 유사도를 계산한다. 상위 3개가 왜 선택됐는지 질문과 원문을 비교한다. 문단을 바꾸면 색인을 다시 만들어야 한다.
3. **Try it · retrieval, live**에서는 예시 질문을 보내 `retrieved top 3 passages`를 열어 본다. 답변에 붙은 인용 번호가 실제로 그 문장을 뒷받침하는지 확인하고, 질문을 바꿔 순위 변화를 본다.
4. 확장 실습 **Retrieve child chunks, return parent documents**는 세 부모 문서를 짧은 문장 단위로 나눠 자식을 임베딩하고, 가장 관련된 자식이 속한 부모 문서를 반환한다. 검색 정밀도와 생성에 필요한 문맥을 함께 관찰한다.
5. 확장 실습 **Expose retrieval as an agent tool**은 `retrieve(question, k)`의 JSON Schema를 제공한다. 모델이 검색을 요청하면 질문을 임베딩하고 상위 문단을 tool 메시지로 추가한 뒤 다시 모델을 호출한다. 산술 질문처럼 검색이 불필요한 입력에서는 바로 답하는지도 비교한다.
6. **Top-K versus GraphRAG** 비교는 국소 질문과 코퍼스 전역 질문에 같은 상위 K 방식이 적절한지 검토한다. 이 예시의 그룹은 사람이 붙인 레이블이므로 실제 그래프 추출의 성능을 보여 주는 실험으로 해석하지 않는다.

유사도는 **관련성 후보를 정렬**할 뿐, 문단의 사실성이나 최종 문장에 대한 충분한 증명을 보장하지 않는다. 상위 K는 점수가 모두 낮아도 K개를 돌려주므로 낮은 점수·근거 부족 신호를 검사한 뒤 문단을 프롬프트에 넣어야 한다. `input_type`의 `query`와 `passage` 구분은 같은 코사인 계산 이전에 모델이 두 입력의 역할을 다르게 표현하도록 한다.

## 2c. Deep Agents와 심층 조사

[Deep Agents](https://nvdli.github.io/NemoClawDLI/nemoclaw/02c-deep.html)

- 긴 조사 업무는 한 대화 기록에 모든 지시와 도구 결과를 쌓으면 문맥 한도 초과, 근거의 영향력 감소, 작업 간 간섭이 생긴다.
- 계획자가 질문을 독립 과제로 나누고, 각 작업자에게 **원래 질문·할당된 과제·필요한 도구**만 준다. 형제 작업자의 이력은 전달하지 않는다.
- 작업자는 발견한 근거와 초안을 공유 가상 파일시스템에 저장한다. 마지막 종합 단계가 저장된 결과를 읽어 출처를 추적할 수 있는 하나의 답변을 만든다. 흐름은 **계획 → 조사 → 보존 → 종합**이다.
- 브라우저의 심층 조사 예시는 강의 절과 선별된 자료에서 3~4개의 독립 과제를 만들고 병렬 작업자의 결과를 모은다. 각 결과는 **확인된 내용, 자료가 덮지 못한 범위(coverage gap), 사용 불가능한 분기**를 구별한다. 종합 단계는 확인된 결과만 인용하고 빠진 근거를 채워 넣은 척하지 않는다.
- 문맥 분리는 추론 이력을 나누는 방법이며 운영체제 접근을 제한하는 샌드박스와 역할이 다르다. Index Agent는 개발자가 검색 파이프라인을 미리 정하고, Deep Agent는 실행 중 계획자가 조사 분기를 만든다. 각 단계 안에는 필요에 따라 ReAct 루프를 둘 수 있다.

### 실습을 따라가는 방법

1. **Try it · plan, investigate, and synthesize**에 조사 질문을 입력한다. 계획이 어떤 독립 과제를 만들었는지 확인한 뒤 작업자별 패널에서 읽은 자료와 작성한 발견을 살핀다. 종합 답변의 각 주장이 어느 분기와 자료에 기대는지 추적한다.
2. **Connect the model** 예시는 LangChain의 `ChatOpenAI`를 활성 모델 경로에 연결한다. `invoke()`는 완성된 메시지를, `stream()`은 부분 메시지를 돌려주는 `Runnable` 인터페이스의 차이를 보여 준다.
3. **Turn the loop into a graph** 예시는 타입이 있는 `get_current_time` 도구를 선언하고 `createReactAgent`로 모델·도구 노드를 잇는다. 실행 후 메시지 궤적에서 도구 요청과 결과를 찾아, 단순 ReAct 루프와 같은 결정을 그래프가 표현함을 확인한다. 단순 루프로 충분한 경우까지 그래프를 도입할 필요는 없다.
4. **Save and combine worker drafts** 예시는 작업자가 공유 메모리 파일시스템에 초안을 쓰고, 종합 단계가 예상한 파일이 모두 존재하며 내용이 비어 있지 않은지 확인한다. 이 예시의 작업자는 외부 검색 도구나 제공된 출처 없이 모델 지식으로 초안을 쓴다. **파일에 저장된 초안은 독립적으로 검증된 근거가 아니다.**

### 이해 확인

- 각 작업자는 원래 질문·자기 과제·필요한 도구만 받는다. 다른 분기의 상세 이력은 받지 않는다.
- 저장소는 작업자의 문맥이 끝나도 결과를 보존하고, 종합 단계에 필요한 정보만 건네기 위한 것이다. 모든 이력을 한 대화에 누적하는 방식을 피한다.
- 문맥 분리는 작업 간 추론 간섭을 줄이고, 샌드박스는 파일·프로세스·네트워크 등 실행 환경의 접근 범위를 제한한다. 서로 다른 실패를 막는다.

## 3a. NemoClaw 실행 환경 연결

[Connect NemoClaw](https://nvdli.github.io/NemoClawDLI/nemoclaw/03a-kickstart.html)

모듈 1~2는 브라우저가 모델 호출과 임시 상태를 관리했다. 모듈 3은 **NemoClaw 청사진**이 구성한 지속 실행 환경으로 이동한다. 역할을 분리하면 모델 엔드포인트는 의미적 응답을 만들고, **OpenClaw 하네스**는 도구·세션 기록·파일 워크스페이스를 관리하며, **OpenShell**은 에이전트 프로세스의 접근 범위를 정책으로 제한한다. 브라우저의 모델 경로와 런타임 안의 모델은 별도 설정이며 서로 다를 수 있다.

### 연결과 인터페이스

1. 강의의 NemoClaw launchable을 실행하고 `<launchable>/dashboard`에서 `my-assistant`의 **Chat with Agent**를 확인한다. 강의는 호환되는 로컬 배포도 대안으로 안내한다. 강의 페이지에 실행 환경의 Base URL을 넣고 **Test connection**을 누른다. 로컬 대안도 아래 네 연결 경로를 제공해야 강의의 검사와 실습을 그대로 사용할 수 있다.
2. 연결 검사는 **`/api/agent` 메타데이터, `/cli/gateway` WebSocket, `/ws/terminal` WebSocket, `/healthz`** 네 경로를 순서대로 확인한다. 어느 경로가 성공했는지 확인하고, 런타임 주소와 전송 경로를 구분한다.
3. 강의 페이지가 실행 환경과 다른 호스트에 있다면 브라우저 접근 세션이 별도로 필요할 수 있다. `apps.run.brev.nvidia.com`은 `_pomerium`, `brevlab.com`은 `CF_Authorization` 쿠키 값을 강의의 **Access session** 입력란에 넣도록 안내한다. 이는 호스트 도달을 허용하는 자격증명이고, 게이트웨이 토큰은 JSON-RPC 작업 권한을 부여하는 별개의 자격증명이다. 자격증명은 강의가 지정한 입력란 밖에 기록하지 않는다.
4. 게이트웨이 토큰은 인증된 `/api/agent` 응답의 `agent.dashboardUrl`에서 발견되므로 토큰 필드는 비워 둔다. 강의에서 요청하는 `operator.admin` 범위는 `models.list`, `cron.add`, `chat.send` 같은 관리 기능을 포함한다.

### 같은 질문을 세 계층에서 보기

| 계층 | 이 단원의 호출 | 확인할 점 |
|---|---|---|
| 직접 모델 | Chat Completions의 HTTP 요청 | 메시지와 모델 인증을 보내지만 OpenClaw 세션·도구는 없다. |
| 런타임 내부 도구 | MCP 등의 발견·호출 계약 | 도구 연결 규약이며 브라우저의 게이트웨이 통신을 운반하지 않는다. |
| 실행 중인 에이전트 | `/cli/gateway` WebSocket의 JSON-RPC | `chat.send`가 게이트웨이 안의 루프를 시작하고 이벤트를 스트리밍한다. |

**Step 1**의 `Hello chat`은 기존 강의 모델 경로로 직접 한 번 호출해 대조군을 만든다. **Step 2**는 게이트웨이 연결 → `models.list`·`cron.list` → 새 `sessionKey`로 `chat.send` 순으로 실행한다. 추적의 `⚙️` 행은 도구 입력, `✓/✗` 행은 도구 결과다. 게이트웨이는 모델의 내부 추론을 전달하지 않으므로 입력·출력 이벤트와 런타임 로그를 근거로 해석한다.

**Step 3**은 임의의 코드를 한 세션에 알려 주고, 코드를 다시 보내지 않은 채 같은 `sessionKey`로 회상시킨다. 이어 `sessions.reset` 후 다시 물어 세션 기록이 사라진 효과를 비교한다. 클라이언트는 매번 대화 전문 대신 키만 보내고 게이트웨이가 서버 쪽 기록을 찾는다. `reset`은 공유 워크스페이스 파일을 지우지 않으므로 실습 지시는 코드를 파일에 쓰지 않게 한다. 마지막 정리는 이 실습이 만든 세션만 대상으로 한다.

실행 환경 상태가 이상하면 **Health check → 결과·로그 확인 → 필요한 복구만 적용**한다. 강의의 복구 셀은 `tools.toolSearch`가 켜져 있고 `exec` 검사가 실패한 경우에만 이를 끄며, 세션 초기화와 재시작은 별도 선택이다. 한 요청의 지연이나 명령 오류만으로 원인을 단정하지 않는다.

## 3b. OpenClaw 하네스와 워크스페이스

[OpenClaw Agent Harness](https://nvdli.github.io/NemoClawDLI/nemoclaw/03b-openclaw.html)

OpenClaw는 모델 호출을 감싼 **에이전트 하네스**다. 세션 기록과 파일 워크스페이스를 사용해 매 턴의 문맥을 구성하고 도구 호출을 진행한다. NemoClaw는 이 하네스를 OpenShell과 함께 구성한다. 에이전트에게 자신의 설정을 설명하라고 묻는 답만 믿지 말고, 운영자 쪽에서 실제 파일을 읽어 대조한다.

| 파일 | 강의에서 맡긴 역할 |
|---|---|
| `SOUL.md` | 인격, 경계, 말투, 가치 |
| `AGENTS.md` | 운영 지시와 규칙 |
| `IDENTITY.md` | 이름과 표시상 정체성 |
| `USER.md` | 사용자 정보와 선호 |
| `TOOLS.md` | 도구별 사용 메모 |
| `HEARTBEAT.md` | 주기적 자율 작업의 점검 목록 |
| `memory/<날짜>.md` | 작업 중 누적되는 일별 원시 기록 |
| `MEMORY.md` | 선별된 장기 기억; 기본적으로 주 세션 문맥에 포함 |
| `skills/<이름>/` | 재사용 가능한 스킬 파일과 부속 자료 |

`MEMORY.md`를 공유·그룹 프롬프트에서 제외하는 기본 문맥 선택은 파일 자체의 접근 제어가 아니다. 실제 읽기·쓰기 가능 범위는 실행 환경의 권한으로 확인해야 한다.

### 실습을 따라가는 방법

1. **Ask the agent to describe itself**에서 워크스페이스 파일과 역할을 말하게 한다. **Read the workspace yourself**의 운영자 읽기 결과와 비교해 자기 보고가 맞는지 확인한다.
2. **Compare message instructions**는 같은 검토 질문을 두 새 세션에 보낸다. 두 번째에만 감사자 관점의 누락 근거 확인을 명시하고 답변을 비교한다. 이는 메시지 지시의 비교이며 `SOUL.md`를 편집하는 실험이 아니다.
3. **The agent edits its own context**는 고유 표식을 가진 선호를 `MEMORY.md`에 추가하도록 요청한다. 먼저 운영자 읽기로 실제 파일 저장을 검증하고, 새 대화에서 그 표식과 참조를 읽어 오게 한다. “저장했다”는 에이전트의 말만으로 성공을 판단하지 않는다.

에이전트가 이후의 자기 문맥을 수정할 수 있다면 후속 실행의 행동도 바꿀 수 있다. 그래서 파일 소유권, 호스트·이웃 에이전트 워크스페이스 접근, 네트워크 정책을 따로 확인한다.

## 3c. 스킬과 상시 실행

[Always-On Agents](https://nvdli.github.io/NemoClawDLI/nemoclaw/03c-always-on.html)

사용자의 현재 입력 외에도 타이머나 다른 에이전트가 실행을 시작할 수 있다. 강의는 모든 지속 실행 메커니즘을 **세션(누구의 문맥인가)·지시(무슨 일을 시키는가)·트리거(언제 시작하는가)**로 비교한다.

| 메커니즘 | 이 강의의 세션 | 지시 위치 | 트리거 |
|---|---|---|---|
| 스킬 | 호출자 세션 재사용 | `skills/<name>/SKILL.md`와 부속 runbook | 실습에서는 명시적 요청 |
| Heartbeat | 주 세션 | `HEARTBEAT.md` | 게이트웨이 타이머, 기본 약 30분 |
| Cron | 실행마다 새 격리 세션 | 예약 작업의 `payload.message` | 실습의 일회성 예약 시각 |
| 하위 에이전트 | 새 문맥, 부모가 핸들 보유 | 부모가 할당한 과제 | 부모가 작업 중 결정 |

이 페이지에서 **실제로 실행하는 것**은 스킬과 Cron이다. Heartbeat와 하위 에이전트는 개념 비교만 한다. 다른 OpenClaw 구성은 Cron에 주 세션, 현재 세션, 명명된 세션을 연결할 수도 있다.

### 실습을 따라가는 방법

1. **Install a practice skill**은 이름·설명 frontmatter가 있는 `SKILL.md`와 runbook을 워크스페이스에 설치하고 두 파일의 읽기 결과로 검증한다. 새 대화에서 스킬 경로를 **명시적으로** 읽도록 요청하고, 가상 장애 사례에 대해 runbook 참조와 다음 단계 제안을 확인한다. 이 결과는 자동 스킬 선택이 아니라 명시적 사용의 증거다. 자동 선택을 시험하려면 경로를 빼고 실제로 파일을 읽는지 다시 봐야 한다.
2. **Schedule, verify, and clean up**은 `cron.add`로 고유한 일회성 작업을 만들고 격리 세션에서 새 파일을 쓰게 한다. 최대 3분 동안 실행 이력과 새로운 파일 참조를 확인한다. `cron.list`로 예약 상태를 보고 `cron.remove`로 실습 소유 작업만 제거한다. 강의 코드는 완료 후 자동 삭제를 요청하고 실패·중지 시에도 정리를 시도한다. 정리 실패 시 기록된 작업 ID로 별도 제거 셀을 실행한다.

예약 작업의 성공은 “에이전트가 하겠다고 말했다”가 아니라 **예약 실행 이력과 일치하는 새 파일**로 입증한다. 격리 세션은 이전 대화 기록을 자동 승계하지 않지만, 공유 파일은 다음 실행에 영향을 줄 수 있다. Hermes도 스킬·기억·예약·메시징을 제공하나 이름이 같은 기능의 기본 권한과 격리 성질까지 같다고 가정하지 않는다.

## 4a. OpenShell 정책과 실행 경계

[OpenShell Sandboxes](https://nvdli.github.io/NemoClawDLI/nemoclaw/04a-safety.html)

OpenClaw는 **무슨 행동을 요청할지** 고른다. OpenShell은 그 요청이 파일·네트워크·운영체제 자원에 **어디까지 닿을지** 정책으로 제한한다. NemoClaw는 둘을 묶은 참조 스택이다. 같은 OpenShell 경계는 Hermes나 다른 에이전트 프로세스에도 적용할 수 있다.

| 계층 | 막으려는 실패 | 확인 방법 |
|---|---|---|
| 프롬프트 지시 | 모델의 부적절한 선택 | 반대되는 외부 입력을 넣어 행동을 평가한다. 문장 지시는 권한 자체를 줄이지 않는다. |
| 하네스 검증 | 허용되지 않은 도구·인자 | 호출 전 결정적 검사와 거절 기록을 본다. |
| 샌드박스 집행 | 허가 밖 파일·네트워크·프로세스 작업 | 활성 정책과 실제 명령 결과를 함께 본다. |

### 네 가지 운영체제 메커니즘

1. **네트워크 네임스페이스(netns)**가 에이전트에 별도 네트워크 스택을 주고 외부 통신을 기본 차단한다. 허용된 출구인 HTTP CONNECT 프록시에서 OPA 정책이 실행 바이너리, 호스트, 포트, 메서드·경로를 검사한다.
2. **Landlock**은 정책에 없는 새 파일 작업을 제한한다. 실제 보장은 호환 모드, OverlayFS, 제한 이전에 열린 핸들 등의 조건을 고려해 확인한다.
3. **seccomp**는 커널 시스템 호출을 걸러 `ptrace`, `mount`, `setuid` 같은 위험한 작업을 제한한다. 거부된 호출은 실행 전에 `EPERM`을 돌릴 수 있다.
4. 에이전트를 **비루트 `sandbox` 사용자**로 실행해 기본 권한을 낮춘다. 이것만으로 권한 상승이 불가능하다고 단정하지 않는다.

### 실습을 따라가는 방법

1. **Ask the box anything**에서 준비된 명령을 한 번에 하나씩 실행해 stdout·stderr, 종료 코드, 완료 여부를 읽는다. 실습은 임시 파일을 정리하고 `SOUL.md`는 수정하지 않고 목록만 본다. 명령 실패는 정책 외에도 미설치, 잘못된 요청, 원격 서비스 오류일 수 있다.
2. **Read live policy**는 운영자 터미널의 `policyGet()`으로 실제 정책 YAML과 활성 상태를 확인한다. 브라우저 정책 지도에서 목적지와 바이너리를 바꿔 일치하는 규칙을 찾는다. 이 지도는 정적 예측이다.
3. **Predict → Confirm → Compare**는 선택한 `curl`의 바이너리·목적지·포트·메서드·경로에 대한 정책 예측과 `openshell sandbox exec`의 실제 결과를 대조한다. 허용된 `inference.local` 요청과 외부 호스트·클라우드 메타데이터 주소 등 제한 대상 후보를 비교한다. 불일치가 나면 요청, 활성 정책, 응답 출처, 평가기 가정을 다시 확인한다.
4. **Operator control plane**은 기존 `operator.admin` 토큰으로 페르소나, 예약, 세션, 모델, 설정의 읽기 메서드를 조사한다. 성공한 읽기만으로 관리 쓰기 권한을 입증하지 않는다. 운영자 평면의 권한은 에이전트 네트워크 허용 규칙과 별개의 축이다.

샌드박스가 허용된 목적지의 **데이터 의미**까지 판정하지는 않는다. 강의의 ‘lethal trifecta’는 **신뢰할 수 없는 입력 + 비공개 데이터 읽기 + 외부 통신 채널**이 결합하는 위험이다. 프롬프트 주입, 도구 오용, 기억 오염에는 출처 확인·도구별 권한·변경 승인·기록 검토가 필요하며, 샌드박스는 그 과정에서 접근 가능한 자원을 줄인다.

## 4b. 현대 CLI 에이전트와 하네스 비교

[Modern CLI Agents](https://nvdli.github.io/NemoClawDLI/nemoclaw/04b-modern-clis.html)

Claude Code, Codex CLI, Cursor, Hermes, OpenClaw는 모두 작업 디렉터리, 도구, 기억, 네트워크를 둘러싼 모델 루프를 제공하지만 **기본 허용 범위·승인·무인 실행·내장 기능**이 다르다. 하네스가 많은 기능을 제공할수록 작성할 코드는 줄 수 있지만 어떤 상태와 동작을 감추는지도 확인해야 한다. 강의는 특정 제품의 이름으로 안전성을 판단하지 않고 **실제 구성**을 검사한다.

비교 축은 파일 읽기·쓰기 경로, 네트워크 출구와 요청 형태, 프로세스 신원, 허가를 사용할 수 있는 바이너리, 스킬·Cron·페르소나의 지속성, 모델 추론 경로다. 강의의 NemoClaw 참조 구성은 쓰기 가능한 경로를 `/tmp`, `/sandbox/.openclaw`, `/sandbox/.nemoclaw`, 작업 디렉터리 등으로 제한하고 나머지 시스템 경로는 읽기 전용으로 취급한다. 네트워크는 기본 거부와 짧은 허용 목록, 바이너리별 경로 조건을 사용한다. 실제 환경에서는 4a의 **활성 정책과 실행 결과**로 다시 확인한다.

### 실습을 따라가는 방법

1. **The same task, weighed across harnesses**에서 Claude Code, Codex CLI, Cursor, Hermes, OpenClaw의 참조 텍스트를 필요한 만큼 선택한다. 같은 과제와 실행 위치를 입력해 각 제품이 감추는 추상화, 기본 가정, 내장 기능을 비교한다. 참조 텍스트는 전체 README 또는 강의 작성 설명으로 구별된다.
2. **Build a CLI agent whose shell is this browser**는 브라우저 런타임을 이용해 작은 명령형 에이전트를 만드는 확장 예시다. 화면에 드러난 상태·도구 계약·허용 범위를 기존 CLI와 비교한다.
3. **Open a real shell**과 **Chat with your agent**는 3a의 실행 환경을 사용한다. `openclaw tui` 같은 전체 화면 대화는 일회성 터미널에서 유지하기 어려워 강의 패널이 동일한 `/cli/gateway`로 대화를 스트리밍한다. 운영자 셸과 `agent <cmd>`가 들어가는 샌드박스의 권한을 분리해 관찰한다.

## 4c. 배포와 후속 학습

[Going Further](https://nvdli.github.io/NemoClawDLI/nemoclaw/04c-going-further.html)

강의 전체는 **루프(모델·도구·관찰) → 워크플로(분기·검색·종합) → 지속 런타임(세션·파일·스킬·예약) → 정책 집행(파일·네트워크·프로세스)**의 연결이다. 모델을 바꿔도 바깥 구조를 재사용할 수 있지만 도구 인자, 출력 형식, 문맥 한도, 취소 동작, 실제 과제 성과를 새 모델에서 다시 시험해야 한다.

### 실제 환경으로 옮길 때

- 강의는 Brev launchable 또는 호환되는 로컬 NemoClaw 배포를 안내한다. 로컬 최소 요구사항은 **4 vCPU, RAM 8 GB, 빈 디스크 20 GB**이고 호스팅된 추론을 쓰면 로컬 GPU는 선택이다. 설치 전 [현행 선행 조건](https://docs.nvidia.com/nemoclaw/latest/get-started/prerequisites)을 확인한다.
- 모델 엔드포인트는 NVIDIA Build의 OpenAI 호환 경로를 사용할 수 있다. 브라우저 강의 키 설정과 별개인 배포에서는 엔드포인트, 키, 모델의 도구 호출·구조화 출력 지원, 계정 할당량을 확인한다. 자체 호스팅이 필요하면 NIM 서버를 대안으로 소개한다.
- 작은 인메모리 색인을 실제 자료로 넓힐 때 NeMo Retriever의 희소·밀집 검색, 점수 결합, 재순위화, 청크 설정을 비교한다. NeMo Data Curator는 중복 제거·필터링을 돕지만 답변 향상을 보장하지 않는다. NeMo Guardrails의 입력·출력 검사와 OpenShell의 운영체제 제한은 서로 다른 계층이다.
- 브라우저 예제의 UI 계약, 즉 **보이는 상태·중간 결과·승인 지점·좁은 동작 버튼**은 다른 호스트로 옮길 수 있다. 인증, 출처 간 접근, 영속성, 파일 권한, 백엔드 도구, 호스트 UI 연결은 환경마다 다시 구현해야 한다.

생산 환경에서는 자료 형태별 검색 충실도, MCP·A2A 등의 프로토콜 경계, 여러 에이전트의 중복 탐색과 협업 품질, 개별 에이전트의 권한 범위가 과제가 된다. 강의는 이 과정에서 같은 과제와 근거를 두고 **결과·경로·정책을 평가**하는 습관을 강조한다.

### 이어서 공부할 NVIDIA 학습 경로

4c는 이 강의를 NVIDIA Agentic AI Learning Path의 **Lesson 6** 실습으로 연결한다. Lesson 1은 LangGraph·Nemotron으로 기본 에이전트 루프를, Lesson 2는 밀집·희소 검색과 재순위화가 들어간 Agentic RAG를, Lesson 3은 과제 성공·도구 사용 품질·실행 경로 효율을 RAGAS와 LLM 평가자로 측정하는 방법을 다룬다. Lesson 4는 NeMo Data Designer의 합성 데이터와 GRPO·LoRA를 통한 모델 맞춤화를, Lesson 5는 계획·하위 에이전트·가상 파일시스템을 결합한 Deep Agent를, Lesson 6은 이 강의의 OpenClaw·OpenShell 안전 경계를 다룬다. 새 모델로 옮길 때는 Lesson 3의 평가 관점을 사용해 같은 과제의 **결과, 도구 호출 경로, 호출량과 지연, 정책 위반**을 비교한다.
