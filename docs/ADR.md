# ADR — HER2 웹 서비스의 주요 결정

작성일: 2026-09-25. [INTENT](intent/INTENT.md)와 [PRD](PRD.md)를 바탕으로 선택의 배경·대안·영향을 기록한다. 최종 구성은 [ARCHITECTURE](ARCHITECTURE.md)에 둔다.

**사용자 확정**은 직접 지정한 사항, **설계 선택**은 위임받아 이번 문서에서 선택한 구현 기준, **잠정안**은 확인 조건이 남은 제안이다. 어느 상태도 구현 성공이나 성능 검증을 뜻하지 않는다. 이후 결정이 바뀌면 기존 기록을 보존하고 대체 결정과 이유를 추가한다.

## ADR-001 — 웹 호스팅과 Docker를 사용한다

- **상태:** 사용자 확정. AWS는 우선 후보이며 세부 배치는 ADR-004의 잠정안.
- **배경:** 사용자가 웹 호스팅 서비스와 Docker 사용을 지정했다. 심사위원이 브라우저에서 입력·3D 비교·보고를 확인하는 형태가 필요하다.
- **결정:** 브라우저 서비스로 제공하고 배포 단위를 Docker 이미지로 관리한다. 개발·호스팅에서 동일한 애플리케이션 이미지를 사용하되 실행 환경의 설정과 비밀키를 분리한다.
- **대안:** 로컬 전용 실행이나 컨테이너 없는 직접 설치는 이번 제공 방식으로 채택하지 않는다.
- **영향:** 배포 재현성과 함께 영속 데이터·HTTPS·접근 정책·이미지 호환성을 확인해야 한다. Docker 사용 자체가 무중단 운영이나 백업을 제공하지 않는다.
- **검증:** 대표 입력 실행, 컨테이너 교체 후 결과 유지, 웹에서의 접근·다운로드.

## ADR-002 — React·TypeScript·Vite와 Mol*를 선택한다

- **상태:** 설계 선택. 버전 조합과 대표 화면의 성능은 검증 전.
- **배경:** 핵심 화면은 후보 선택·비교표·진행 상태·3D 구조가 서로 반응하는 작업 화면이다. 기존 INTENT에는 검색 노출이나 서버 렌더링 요구가 없고 분석은 Python 영역에 둔다.
- **결정:** React·TypeScript로 UI를 구성하고 Vite로 개발·빌드한다. React Router로 화면과 결과 URL을 연결하며 Mol*로 분자 구조를 표시한다. React는 UI 라이브러리, Vite는 빌드 도구라는 역할을 구분한다.

| 대안 | 이번 프로젝트에서의 판단 |
|---|---|
| React + Vite | 브라우저 중심 화면과 Python API를 직접 연결하기 적합. 라우팅·조회·로딩·오류 처리는 명시적으로 구성해야 함 |
| Next.js | 서버 렌더링과 React 서버 기능이 필요해지면 재검토. 현재 3D·상호작용 부분은 클라이언트가 필요하며 추가 서버 역할의 필요가 아직 없음 |
| Vue + Vite | 분자 viewer를 결합할 수 있는 대안. 현재 Mol* 공식 문서의 React 상태 연동 예제를 직접 참고할 수 있어 React를 선택하며, Vue의 성능이 낮다고 판단한 것은 아님 |

**선택 근거:** Mol* 문서는 구조의 사슬·잔기 선택과 선택 이벤트를 React 상태에 연결하는 예제를 제공한다. 이는 근거표와 3D 연결의 구현 참고가 된다. React 문서는 Vite 구성을 안내하면서 라우팅·데이터 조회 등을 직접 구성해야 하는 부담도 설명한다. Next.js는 상태·이벤트·브라우저 API 사용에 Client Components를 안내한다. 이러한 기능과 현재 요구를 비교한 설계 판단이며 성능 우위를 실측한 결과가 아니다.

출처: [Mol* 선택과 이벤트](https://molstar.org/docs/plugin/selections/), [React의 Vite 구성과 고려사항](https://react.dev/learn/build-a-react-app-from-scratch), [React Router 설치](https://reactrouter.com/start/declarative/installation), [Next.js 서버·클라이언트 구성](https://nextjs.org/docs/app/getting-started/server-and-client-components).

**영향과 검증:** 정적 웹 배포가 가능하지만 입력 검증·접근 제어는 API가 맡아야 한다. 대표 구조 표시, 후보 전환, 표에서 사슬·잔기 강조, viewer 해제·재생성을 먼저 확인한다. 실측 전 프레임워크 선택만으로 빠른 3D 렌더링을 보장하지 않는다. 스타일링 라이브러리와 별도 디자인 시스템은 지금 필수 의존성으로 추가하지 않는다.

## ADR-003 — Python API와 분석 worker를 분리한다

- **상태:** 설계 선택. NAT·모델 조합은 2026-09-26 실측 확인 — `nvidia-nat[langchain]` 1.9.0(Python `>=3.11,<3.14`) + `nvidia/nemotron-3-super-120b-a12b`, `tool_calling_agent` + 커스텀 도구 7개 + 스트리밍 동작 확인([nat-agent-loop.md](topics/her2/nat-agent-loop.md)). 분석 라이브러리(Biopython·freesasa 등, 로직 A쪽) 조합은 미검증.
- **배경:** 기존 분석 설계는 Python 도구와 NAT를 사용한다. 구조 예측과 분석은 웹 요청보다 오래 걸릴 수 있고 브라우저를 닫아도 상태를 남겨야 한다.
- **결정:** FastAPI는 접수·조회·파일 전달을, 별도 Python worker는 분석을 맡는다. 초기에는 같은 코드·이미지를 두 실행 명령으로 운영하며 브라우저는 저장된 작업 상태를 polling한다.
- **대안:** API 요청 안의 전체 분석과 FastAPI `BackgroundTasks`만 사용하는 방식은 초기 구현이 단순하지만 긴 계산과 재시작 후 상태 관리를 별도로 해결해야 한다. WebSocket·SSE는 실시간 양방향 제어 요구가 없어 초기 필수로 두지 않는다.
- **영향:** 작업·단계 상태 저장과 중단 처리가 필요하다. 외부 API 호출의 성공 여부를 모르는 상태에서 자동 재시도하지 않아야 한다.
- **검증:** 작업 접수 후 새로고침, API·worker 각각의 재시작, 외부 timeout, 중복 접수에서 상태·결과 일치 확인.

FastAPI 공식 문서도 무거운 백그라운드 계산에 별도 실행 도구를 고려하도록 안내한다. 분리 방식과 polling 선택은 프로젝트 요구에 따른 판단이다. [FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/)

## ADR-004 — 초기 AWS 후보는 단일 EC2와 Docker Compose다

- **상태:** 잠정안. PRD Q01–Q03·Q06 확인 후 배치 확정; 자원 생성·비용 지출은 아직 하지 않음.
- **배경:** 초기 목적은 전체 데모이며 현재 고가용성·다중 호스트 요구는 없다. 팀은 서비스 1명과 분석 2명으로 구성되어 있다.
- **결정 제안:** EC2 한 대에서 `web / api / worker / db`를 Compose로 운영한다. Caddy가 정적 파일·HTTPS·API 프록시를 맡고, DB·파일은 EBS 영속 볼륨에 둔다. 모델 추론은 외부 API 경로를 우선 검증한다.

| 대안 | 장점과 부담 |
|---|---|
| EC2 + Compose | 한 호스트에서 전체 구성을 재현하기 쉽고 운영 대상을 제한할 수 있음. OS·패치·백업·복구를 팀이 맡고 단일 장애 지점을 감수 |
| ECS + Fargate | 호스트 서버 관리 부담을 줄이는 선택. 태스크·서비스·네트워크·영속 저장소를 별도로 구성해야 하므로 필요가 확인될 때 재검토 |
| 정적 프런트엔드와 별도 API 호스팅 | 화면 배포를 분리할 수 있음. 초기에는 배포·도메인·접근 정책을 여러 곳에서 맞춰야 함 |

**근거와 한계:** Docker는 Compose의 단일 서버 운영 경로를 문서화한다. EC2는 가상 서버, EBS는 영속 블록 저장소를 제공하며 Fargate는 서버 관리 없이 컨테이너를 실행하는 선택이다. 이것만으로 EC2가 최저 비용이거나 특정 규격으로 충분하다고 결론내리지는 않는다.

출처: [Docker Compose 운영](https://docs.docker.com/compose/how-tos/production/), [EC2 개요](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/concepts.html), [EBS 볼륨](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volumes.html), [ECS Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), [Caddy HTTPS](https://caddyserver.com/docs/automatic-https).

**확정 조건:** 예산·가동 기간·계정·도메인·입력 정책 확인, 대표 분석의 CPU·메모리·디스크·외부 호출 시간 측정. 비용은 EC2 가동·EBS·공인 주소·트래픽·백업·도메인·외부 API를 함께 산정한다. 무료 사용이나 지원 크레딧을 전제하지 않는다. TLS 발급 경로는 실제 도메인·네트워크 조건에서 확인한다.

**2026-09-25 추가 확인:** 사용자는 해커톤 기간에만 운영하며 서버의 에이전트 실행에 필요한 성능을 고려하기를 원한다. 단기 운영은 확인됐지만 정확한 가동 시간과 총예산 상한은 미확정이다. 기존 외부 모델 API 설계를 유지하며, 에이전트 실행과 모델 자체의 추론 호스팅을 구분한다.

**사양 검토 보완 — 잠정안:** 4 vCPU·16 GiB RAM의 `m7i.xlarge`를 초기 부하 검증 후보로 삼는다. 웹·API·worker·DB를 한 호스트에서 실행할 여유를 두려는 설계 판단이며 실측 요구량은 아니다. 8 vCPU·32 GiB급은 CPU·메모리 부족이 측정될 때 재검토하고, GPU 서버는 모델 자체 호스팅으로 범위가 바뀌는 경우 별도로 결정한다. 비용이 적을 것이라는 기대만으로 고사양을 확정하지 않는다. [AWS 사양](https://docs.aws.amazon.com/ec2/latest/instancetypes/gp.html), [NAT의 기본 GPU 비필수 조건](https://docs.nvidia.com/nemo/agent-toolkit/latest/quick-start/installing.html)

## ADR-005 — 작업 상태는 PostgreSQL, 큰 파일은 영속 볼륨에 둔다

- **상태:** PostgreSQL과 DB 기반 작업 접수는 설계 선택; 파일 볼륨 배치는 ADR-004에 종속된 잠정안.
- **배경:** API와 worker가 입력·실행·결과 상태를 공유해야 하며, 새로고침이나 컨테이너 교체가 기록을 지우면 안 된다. 초기에는 worker 하나가 작업을 순차 처리한다.
- **결정:** PostgreSQL에 작업·근거·결과 참조를 저장하고 작업 테이블을 짧은 트랜잭션으로 점유한다. 구조·원본 입력·결과 파일은 DB 밖에 저장하고 ID·해시로 연결한다. 별도 메시지 브로커는 초기 구성에 추가하지 않는다.
- **대안:** 메모리 저장은 재시작 복구에 부적합하다. SQLite도 소규모 대안이지만 이 설계는 API와 worker의 동시 상태 갱신을 DB 서비스로 모은다. Celery·Redis 또는 SQS는 실행량·worker 수가 늘 때 재검토한다.
- **영향:** 점유·생존 확인·중단 처리를 직접 구현하고 검증해야 한다. DB 잠금만으로 외부 호출의 중복·유실이 해결되지는 않는다. 한 호스트의 볼륨은 호스트 장애를 해결하는 백업이 아니며 다중 호스트 확장 전 저장 방식을 바꿔야 한다.
- **검증:** 중복 접수·worker 강제 종료·산출물 저장 중 종료·컨테이너 재생성·백업 복구에서 상태와 파일 참조 확인.

PostgreSQL은 `SKIP LOCKED`를 일반 조회 대신 queue 형태 테이블의 잠금 경합 회피에 사용할 수 있다고 설명한다. 실제 점유 방식은 초기 worker 수에 맞게 단순하게 구현한다. [PostgreSQL SELECT 잠금](https://www.postgresql.org/docs/current/sql-select.html)

## ADR-006 — 계산 근거와 에이전트 설명을 분리한다

- **상태:** 기존 INTENT의 경계를 계승한 설계 선택.
- **배경:** 구조 신뢰도·접촉 지표를 결합력이나 치료 효과로 오해하지 않도록 해야 한다. 모델의 자유로운 설명만으로 후보를 판정하면 근거·조건을 되짚기 어렵다.
- **결정:** 검증 가능한 함수가 입력 대응·계산값·보류 조건을 만들고, 에이전트는 허용된 작업 선택과 근거에 한정된 설명을 맡는다. 의견은 후보·조건·판단 항목·근거 ID에 연결한다. 없는 값과 충돌 근거를 종합 점수에 숨기지 않는다.
- **대안:** LLM이 원자료를 읽고 최종 점수·후보 순위를 직접 만드는 방식은 채택하지 않는다. 모든 후보에 같은 예측을 무조건 실행하는 방식도 기존 자료 활용·보류 분기를 충족하지 못한다.
- **영향:** 과학적 정의·임계값·정답 근거는 별도 검토가 필요하며 이 ADR에서 임의 확정하지 않는다. 계산 완료와 설명 생성 완료를 구분한다.
- **검증:** 입력 불일치·당쇄 자료 누락·지표 충돌·API 실패에서 근거 없는 수치나 효능 판정이 생기지 않는지 확인한다.

근거: [INTENT의 경계](intent/INTENT.md#5-지켜야-할-경계), [기존 판단 분기](topics/her2/agent-design.md#단계가-고정-파이프라인이-되지-않게-할-분기), [검증 기준](topics/her2/validation.md).

## ADR-007 — 화면과 보고서는 같은 결과 스냅샷을 사용한다

- **상태:** 설계 선택. 구체적 연동 스키마는 서비스·분석 담당 검토 전.
- **배경:** 3D·비교표·다운로드가 서로 다른 후보나 설정을 가리키면 검토 근거를 확인할 수 없다.
- **결정:** 실행별 구조화 결과를 저장하고 화면·보고서·JSON·CSV가 이를 공통으로 사용한다. 후보·조건·구조·잔기 대응과 schema version을 유지하며 재실행은 이전 결과를 덮어쓰지 않는다.
- **대안:** 화면과 보고서에서 각자 계산·요약하면 결과가 달라질 수 있어 채택하지 않는다. 전역 캐시나 타 사용자 간 결과 재사용은 데이터 정책 확정 전 도입하지 않는다.
- **영향:** 원본과 파생 결과의 참조·파일 완성 시점을 관리해야 한다. 3D는 표시 책임만 지고 분석 정렬·잔기 대응을 별도로 추측하지 않는다.
- **검증:** 후보·조건 전환, 재실행 후 이전 결과 조회, 화면·보고서·다운로드의 ID·값·보류 이유 일치.

## ADR-008 — 공개 자료와 본인 임시 결과로 데모 범위를 제한한다

- **상태:** 공개 자료만 입력, 누구나 서비스 실행·열람, 개별 결과는 공개 목록 없이 본인만 임시 조회·다운로드하는 방향은 2026-09-25 사용자 확정. 마지막 세션 연결 후 30분 유예·만료 삭제는 추천을 요청받아 제시한 설계안이며 구현·실측 검토 전.
- **배경:** 사용자는 사이트 이탈 후 결과가 남지 않기를 원했다. 공개 자료 데모로 범위를 정했으며 비공개·민감 자료 지원은 이후 검토로 남긴다. 직접 입력·업로드도 공개 자료만 허용한다.
- **초기안:** 유효한 세션 연결이 끊긴 뒤 유예 기간 안에는 같은 결과를 복구하고 만료 후 접근을 차단·정리한다. 새로고침·탭 전환 자체로 즉시 삭제하지 않는다. 명시적 종료·삭제와 실행 중 안전한 정리 방식, 외부 호출의 취소 가능성, 실제 정리 완료 기한은 서비스·로직 계약에서 검토한다.
- **대안:** 브라우저 이탈 이벤트만으로 즉시 삭제하는 방식은 신호 누락과 새로고침 복구 문제가 있다. 영구 공개 결과 목록은 사용자 선택에 맞지 않는다.
- **영향:** ADR-005의 영속 저장과 ADR-007의 결과 재조회는 허용 보관 기간 내에 적용하도록 범위를 좁힌다. 백업이 삭제한 임시 결과를 다시 노출하지 않도록 대상·만료·복구 정책을 검토한다. 실행 상태와 세션 만료·삭제 상태는 별도로 관리하며, 비밀 URL이나 로그인 방식은 아직 확정하지 않는다.
- **검증:** 유예 내 새로고침·재접속, 종료 신호 누락, 만료 후 파일/API 접근 차단, worker 실행 중 만료, 정리 실패·재시작·복구에서 임시 자료 수명과 상태 확인. 30분 값은 공개 자료 데모에서 검증 후 조정한다.

브라우저 종료 관련 이벤트는 항상 발생하지 않으므로 즉시 삭제나 외부 서비스 무보관을 보장하는 근거로 쓰지 않는다. [MDN pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event), [조사·사용자 인터뷰](frontend-hosting/overview.md), [삭제·외부 API 검토](frontend-hosting/hosting-requirements.md)

## 미결정 사항 관리

공개 접근·자료 범위와 임시 결과 방향은 확인됐으며, 남은 예산·세부 접근/삭제·과학적 판정 기준·모델 제공 경로와 계정은 [PRD Q01–Q06](PRD.md#8-미결정-항목과-결정-시점)에서 관리한다. 답변·실측이 생기면 관련 ADR 상태와 ARCHITECTURE를 함께 갱신한다.

외부 기술 문서는 2026-09-25에 확인했다. 공식 문서의 기능 설명과 이 프로젝트의 선택 판단을 구분했으며, 모델 API 호출·패키지 설치·호스팅·비용 검증은 수행하지 않았다. 후속 서비스 조사에서 수행한 RCSB 공개 데이터 조회는 모델 호출·분석 실행 검증과 구분한다.
